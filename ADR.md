# Архитектурные решения

Дата: **12.11.2026**. Два кратких ADR по требованиям
[исходного задания](docs/source/assignment.md). Статус «принято» относится
к архитектурному выбору, а не подтверждает готовность реализации.

## ADR-001. Четыре сервиса с явным владением данными

**Статус:** принято.

**Проблема.** Задание требует минимум два независимо развёртываемых
Python/FastAPI-микросервиса. Нужно отделить пользователей, бизнес-правила
брони и работу LLM, сохранив работоспособность формы при отказе помощника.

**Решение.** В монорепозитории выделены Gateway, Users, Booking и Assistant
с собственным React-интерфейсом. Gateway предоставляет HTTP/MCP/SSE и
выполняет всю авторизацию. Users владеет учётными записями, правами и
сессиями; Booking — пространством, бронями и предметными инвариантами;
Assistant — диалогами и вызовами LLM через общий MCP. В одном экземпляре
PostgreSQL используются три отдельные БД с собственными доступом и
миграциями; у Gateway своей БД нет. Чужие таблицы сервисы не читают.

**Альтернатива.** Модульный монолит проще для масштаба тестового, но не
выполняет требование микросервисов. Схема из трёх сервисов с пользователями
в Gateway сохраняла бы минимум задания, однако не давала домену
пользователей отдельного владельца.

**Последствия.** Изоляция отказов AI и границы ответственности становятся
явными. Появляются дополнительные процессы, миграции и межсервисные
контракты. Четыре сервиса — наш выбор декомпозиции, а не требуемое заданием
количество; новые домены не обязаны автоматически становиться сервисами.

Подробно: [D-014, D-109, D-113, D-117](docs/decisions.md),
[схема и границы компонентов](docs/architecture.md).

## ADR-002. Core NATS для запросов, JetStream и outbox для надёжных действий

**Статус:** принято.

**Проблема.** Обычным межсервисным запросам нужен ответ, а бизнес-действия
должны переживать временный отказ получателя. Например, отключение
сотрудника не должно терять задачу отмены его броней при недоступном Booking.
Отдельные commit в БД и публикация сообщения оставляют окно потери события.

**Решение.** Gateway вызывает Users, Booking и Assistant через Core NATS
request/reply. Надёжные фоновые команды и события используют JetStream
с transactional outbox: изменение и событие сохраняются одной локальной
транзакцией; отправитель отмечает публикацию после подтверждения брокера.
Повтор сохраняет ID события, потребитель обрабатывает его идемпотентно
и подтверждает после commit. RPC/reply subjects не включаются в сохраняемые
потоки. Внешние HTTP/MCP/SSE и HTTP MCP-вызов Assistant → Gateway сохраняют
свои протоколы.

**Альтернатива.** Внутренний HTTP для запросов и отдельный брокер для
фоновых действий. Для надёжной публикации — CDC вместо outbox;
сохранение всех RPC в JetStream добавляло бы ненужную долговечность
обычным запросам. Прямая публикация после commit не устраняет риск потери.

**Последствия.** Core и JetStream работают на одном сервере NATS;
нужны outbox-процессы, потребители, повторы и контроль выполнения.
Повторная доставка допустима, гарантии «ровно один раз» не предполагаются.
Тайм-аут RPC не доказывает отсутствие commit: повтор подтверждения брони
использует прежний ключ идемпотентности. При недоступном Booking отзыв
сохраняется, а администратор видит незавершённую отмену до её выполнения.

Подробно: [D-111, D-112, D-120, D-124](docs/decisions.md),
[текущий внутренний транспорт](docs/implementation/service-rpc.md).
