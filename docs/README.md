Они задают целевое поведение; реализация и результаты проверок описаны отдельно.

Единая структура пяти приложений и правила публичной документации — D-138.

## Пять ТЗ

| Документ                       | Область                                           |
| ------------------------------ | ------------------------------------------------- |
| [Frontend](spec/frontend.md)   | React: план, форма, чат и админка                 |
| [Gateway](spec/gateway.md)     | HTTP/MCP/SSE, авторизация и права                 |
| [Users](spec/users.md)         | Пароли, здания, веб- и OAuth-сессии               |
| [Booking](spec/booking.md)     | Пространство, время, конфликты, история и события |
| [Assistant](spec/assistant.md) | Pydantic AI, OpenRouter, диалоги, MCP и архив     |

Каждое ТЗ описывает ответственность, сценарии, данные, ошибки и критерии приёмки.
Подробное правило находится у владельца; остальные компоненты ссылаются на него.
Исходное задание отделено от принятых продуктовых и технических решений.
Модель OpenRouter выбрана в D-127; предложение и сворачивание чата — D-128/D-129;
единый Nginx и Docker — D-130; структура публичного репозитория — D-138.

Приложения находятся в `apps/frontend`, `apps/gateway`, `apps/users`,
`apps/booking`, `apps/assistant`, общая библиотека — в `packages/platform`.
Конфигурации `compose.dev.yaml` и `compose.prod.yaml` отделяют режимы и данные;
запуск, зависимости и проверки выполняются только в Docker.

Для приёмки нужен сквозной путь: вход → доступный план → ручная или
подготовленная реальной LLM через MCP форма → подтверждение → одна запись →
обновление другого клиента и архивирование чата. Дополнительно проверяются
гонки с настоящим хранилищем, безопасный повтор, отказ AI и сохранность данных.
Собственный HTTP-клиент не заменяет проверку готового стороннего MCP-приложения.
