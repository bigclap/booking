# ТЗ: сервис Assistant

Версия требований: 12.11.2026. Целевая система, а не подтверждение реализации.
Основания: [исходное задание](../source/assignment.md),
[решения](../decisions.md), [архитектура](../architecture.md).
Смежные ТЗ: [Frontend](frontend.md), [Gateway](gateway.md),
[Users](users.md), [Booking](booking.md).

## 1. Назначение и граница

Assistant — независимо развёртываемый Python/FastAPI-сервис со своей БД
PostgreSQL. Использует **Pydantic AI** внутри нашей обвязки, реальную LLM
через OpenRouter и общий удалённый MCP — D-114. Пользователь выбрал
`~deepseek/deepseek-flash-latest` — D-127; модель задаётся окружением.
Имитация не доказывает выполнение требования о реальной LLM.

Наши обязанности: API чата, хранение сообщений, жизненный цикл диалога,
управление обработкой, промпты, события и ошибки. Собственного логина,
ролей, каталога пространства и правил бронирования в Assistant нет.
Пользователя удостоверяет Gateway, права проверяются там же.

Первая версия встроенного помощника подбирает ресурс и готовит **новую**
бронь. Перенос и отмена через встроенный чат отложены — D-043.
В интерфейсе и общем клиентском MCP эти операции сохраняются:
ограничение Assistant не меняет прав других клиентов.

## 2. Данные и владение

| Данные                        | Требуемый смысл                                                                                     |
| ----------------------------- | --------------------------------------------------------------------------------------------------- |
| Диалог                        | ID, пользователь, активный/архивный, время создания/архивирования, причина архива                   |
| Сообщение                     | ID, диалог, роль/тип, содержимое и структурированные предложения, порядок, время, состояние         |
| Обработка ответа              | ID запуска, исходный диалог/сообщение, состояние, результат/ошибка; защита от параллельного запуска |
| История инструментов          | Связь вызовов и результатов для корректного контекста и диагностики без секретов                    |
| Outbox/обработанные сообщения | Надёжная публикация сохранённых изменений и дедупликация межсервисных действий                      |

Сессия входа, диалог, запуск модели и предложение формы — разные сущности.
Предложение может быть содержимым сообщения/параметрами ссылки, но не
отдельной сущностью бронирования с TTL и удержанием ресурса.
Assistant не читает таблицы Users и Booking. История сохраняется после
перезапуска, автоматического удаления архива по сроку нет — D-104.

## 3. Основной сценарий

1. Сотрудник открывает встроенный чат. Gateway передаёт проверенный контекст
   пользователя и выбранного здания.
2. Сотрудник описывает место или переговорную. Assistant получает недостающие
   обязательные параметры и актуальные данные через MCP.
3. По умолчанию поиск ограничен выбранным зданием и доступом — D-084/D-085.
   Другое здание не подставляется молча.
4. Помощник возвращает текст и проверяемое структурированное предложение:
   конкретные ресурс/здание, дату, начало/конец по Москве, число участников
   для комнаты. Предложение соответствует результатам инструментов.
5. Frontend показывает ресурс на плане и предзаполняет общую форму.
   Пользователь может исправить параметры, видит конечный выбор и подтверждает.
6. Только успешная запись Booking означает созданную бронь. Конфликт,
   валидация и утрата доступа показываются как отказ, а не как успех.

Учитываются тип ресурса, место или помещение целиком, необходимость уединения,
оснащение и окружение. Переговорную можно использовать для индивидуальной
работы. Конкретное место внутри и комната целиком — разные ресурсы,
связанные правилами конфликтов Booking. Число участников комнаты обязательно;
превышение посадочных мест даёт предупреждение, не запрет.

Assistant не выдумывает обязательные данные, свободные слоты и оборудование.
При отсутствии варианта нельзя выдавать занятый/неподходящий ресурс
за подходящий. Порядок уточнений и альтернатив проверяется на реальной
модели и пока не фиксируется — D-101.

## 4. Инструменты и делегированный доступ

Assistant обращается к тому же HTTP MCP-входу Gateway, что внешний клиент —
D-053/D-124. Обхода к бизнес-API, базе Booking или неограниченному служебному
инструменту нет. Внутренний адрес допустим при том же контракте и авторизации.

Встроенному сценарию нужны чтение доступных зданий, планов/ресурсов/оснащения,
временной политики, поиск и занятость, подготовка параметров формы.
Административные инструменты, перенос и отмена встроенному сценарию первой
версии не подключаются. Общий MCP остаётся эквивалентом бэка сотрудника — D-103.

Каждый запуск получает полномочия именно текущего пользователя, без отдельного
входа в Assistant. Их нельзя задавать текстовым `userId` или аргументом модели.
Переиспользование клиента не смешивает заголовки, cookies и MCP-сессии людей.
Credentials добавляются программно вне промпта; пользовательский ввод
и данные инструментов не расширяют права и не подменяют системные инструкции.

Веб-cookie не становится автоматически внешним MCP-токеном. Выдача, срок
и отзыв делегированных полномочий согласуются с Users/Gateway; OAuth
Authorization Code + PKCE внешнего MCP уже выбран D-115.
Совместимость рантайма, MCP SDK и реального клиента проверяется интеграцией.

## 5. Предложение и подтверждение

Предложение — параметры предзаполнения в URL без таймера и отдельной записи
предложения в БД — D-118. Оно не удерживает ресурс и не даёт прав.
Прошедшая дата оставляет поле даты пустым с сохранением прочих параметров.
Владелец определяется текущим удостоверенным контекстом, не содержимым ссылки.

Во встроенном интерфейсе новый ответ со структурированным `proposal` сразу
открывает заполненную форму на карте без URL-перехода и дополнительного клика —
D-128. Сырой URL в тексте не показывается; кнопка остаётся для повторного
открытия и архива. Во внешнем чате агент показывает ссылку из MCP пользователю.
Контракт предложения общий, различается его представление в клиенте.

Любая новая бронь создаётся только после подтверждения в нашей форме.
Текст модели, повторный tool call и чтение архива не исполняют создание.
На отправку формы действует идемпотентность Booking: один ключ — одна бронь;
потеря ответа не требует нового ключа.

Внешний агент подключается к MCP напрямую, без Assistant. Он получает ссылку
на нашу форму, пользователь при необходимости входит и подтверждает.
Результат показывается у нас, callback во внешний чат не нужен — D-121.
Привязка предложения к первоначальному пользователю и TTL не добавляются;
текущие права и правила проверяются при подтверждении.

## 6. Жизненный цикл диалога

- Один активный диалог пользователя общий для всех вкладок — D-105.
  Перезагрузка и повторное посещение восстанавливают незавершённый диалог.
- Успешное создание **любой** брони этим пользователем архивирует текущий
  диалог, даже если он не участвовал в ручной форме — D-082.
  Изменение/отмена существующей брони не объявлены таким триггером.
- «Новый диалог» архивирует текущий без создания брони — D-099.
  Следующее обращение начинает чистый контекст. Пустой следующий диалог
  можно создавать при первом сообщении, сохраняя единый вид во вкладках.
- Ошибка создания брони и простое открытие формы диалог не архивируют.
- Сворачивание, крестик, Escape, скрытие чата при показе формы и повторное
  раскрытие меняют видимость, а не lifecycle — D-129. Текущий диалог,
  сообщения и неотправленный черновик сохраняются; из видимости нельзя
  выводить команду архивирования или создания нового диалога.
- Архив доступен владельцу только для просмотра. Его открытие не вызывает
  модель/инструменты, не продолжает диалог и не исполняет прошлые действия.
- Уже начатый ответ после архивирования сохраняется в **исходном** диалоге —
  D-108. Он не попадает в новый и не открывает старый заново. Специальный
  механизм отмены генерации сейчас не требуется.

Архивирование по созданной брони — надёжное межсервисное действие с устойчивым
ID события. Повтор не архивирует следующий диалог; позднее событие не должно
закрыть диалог, начатый уже после соответствующей брони. Обработчик связывает
событие с нужным диалогом и фиксирует результат до подтверждения сообщения.
Порядок близких по времени брони, нового диалога и завершения ответа проверяется
отдельно. Точная корреляция/порядок — контракт реализации; распределённая
транзакция Booking ↔ Assistant не требуется.

Gateway проверяет доступ к диалогу. Отключённый аккаунт не получает сервис
или архив. Старое предложение не обходит актуальный доступ к зданию:
план, поиск и подтверждение заново проверяются общим клиентским бэком.

## 7. Обработка сообщений и контекст

Во время ответа новая отправка блокируется во всех вкладках, без очереди —
D-106. Сервер атомарно допускает один активный запуск на пользователя:
блокировки кнопки недостаточно. После успеха, ошибки или восстановления
зависшего запуска отправка доступна. Вызов LLM не удерживает транзакцию БД.

Полная история отделена от контекста запроса. В LLM передаётся последняя
часть активного диалога, старые сообщения обрезаются — D-122.
Системные инструкции и текущий запрос сохраняются; пары вызов/результат
инструмента не разрываются. Автоматического резюме и нового диалога
из-за размера истории нет. Архивы в новый контекст не добавляются.

Модель, численный бюджет контекста, число tool calls, тайм-аут и предел
повторов задаются конфигурацией после интеграционной проверки.
Пределы выполнения конечны; ошибка/лимит освобождают состояние обработки.
Произвольный продуктовый лимит сообщений и срок хранения не вводятся.
После перезапуска пользователь не остаётся навсегда в `busy`;
неизвестно завершённый запуск не повторяет изменяющие действия вслепую.

## 8. Взаимодействие и события

Gateway вызывает Assistant через Core NATS request/reply. Отправка сообщения
подтверждает принятие и ID запуска, не держит RPC до завершения генерации.
Сообщения, обработка, предложения и архивирование обновляются через
Gateway SSE во всех вкладках. Детализация потоковых фрагментов задаётся
контрактом; каждый токен не обязан попадать в надёжный журнал.

Сохранённые изменения/события согласуются через outbox своей БД;
надёжные межсервисные действия — JetStream. Потребитель подтверждает
сообщение после commit и обрабатывает повторы идемпотентно.
Событие содержит ID пользователя/диалога/запуска/сообщения и порядок/версию,
чтобы поздний фрагмент не дописался в другой диалог и не откатил состояние.

После переподключения UI получает актуальный снимок диалога, сообщений
и запуска без новой генерации и проигрывания всех событий — D-110.
Снимок и подписка согласуются по контракту Gateway; источник истины —
сохранённое состояние Assistant.

## 9. Отказы и конфигурация

Отказы OpenRouter/MCP/сети, лимит выполнения и невалидный ответ получают
понятное состояние чата. Частичный текст не выдаётся за завершённую бронь.
Некорректное предложение не открывает форму с выдуманным ресурсом.
Актуальную доступность окончательно проверяет Booking при подтверждении.

При отказе Assistant/LLM ручные каталог, план и форма работают независимо,
через Gateway → Booking. Их загрузка и запись не ждут исправности AI.
Ключ OpenRouter хранится только на сервере; токены, пароли и ключи
не входят в промпты, ответы, URL предложений и журналы.

README описывает модель/провайдера, MCP endpoint, промпты, контекстное окно,
тайм-ауты, повторы и проверку реального вызова. Версии закрепляются
в зависимостях; установка, запуск и проверки — только в Docker.
`requestId`/`traceId` связывают запрос, запуск, MCP-вызов и ответ.

## 10. Приёмка

1. Развёрнутый чат вызывает реальную OpenRouter-модель, получает актуальные
   данные через общий MCP; два пользователя не смешивают полномочия.
2. Место и переговорная подбираются с конкретными ресурсом/интервалом;
   число участников уточняется. Предложение видно на плане и в форме,
   до подтверждения записи нет.
3. Устаревшая доступность, выдуманные данные и ошибка модели не создают
   бронь; конфликт после предложения показывается в форме.
4. Перезагрузка и вторая вкладка восстанавливают общий диалог; второе
   сообщение во время ответа не запускает параллельную обработку.
5. Ручная и подготовленная помощником успешные новые брони архивируют чат.
   Повтор события не архивирует следующий, ошибка брони сохраняет текущий.
6. «Новый диалог» даёт чистый контекст; архив читается без LLM/MCP.
   Поздний ответ остаётся в исходном диалоге.
7. Длинный контекст обрезается корректно, полная история переживает рестарт.
   Ошибка/перезапуск не оставляют вечную блокировку отправки.
8. Обрыв SSE восстанавливается снимком без повторной генерации.
9. При отказе OpenRouter, MCP помощника и всего Assistant ручной сценарий
   работает. Сбои проверяются автотестами или воспроизводимо вручную,
   с командами и результатами.

Уточнения/альтернативы проверяются после выбора модели. Промпты можно
уточнять по результатам без изменения серверных прав и правил брони.
Общие материалы сдачи — в [индексе документации](../README.md).
