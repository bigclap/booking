# ТЗ: Gateway

Версия требований: 12.11.2026. Целевое поведение, а не отчёт о готовности кода.
Основания: [исходное задание](../source/assignment.md),
[решения](../decisions.md), [архитектура](../architecture.md).
Оставшиеся параметры реализации — в [очереди](../questions.md).
При пересмотре применяется последнее принятое решение.

## 1. Назначение и границы

Gateway — независимо развёртываемый Python/FastAPI-сервис и единый публичный
вход для React, внешнего MCP-клиента и встроенного Assistant. Выполняет всю
авторизацию и проверку прав, собирает ответы для фронтенда и доставляет SSE.

Gateway не имеет своей БД. [Users](users.md) владеет пользователями, паролями,
назначенными правами и сессиями; [Booking](booking.md) — пространством и бронями;
[Assistant](assistant.md) — чатами и LLM. Правила времени и конфликтов
исполняются Booking. Gateway не содержит их второй реализации и не обращается
к чужим таблицам. Сервисы остаются независимо развёртываемыми в монорепозитории.

## 2. Публичный вход и BFF

UI и API публикуются на одном origin через Nginx: приложение `/`,
HTTP API `/api/`, MCP `/mcp`; SSE проходит через Gateway. Служебные endpoints,
БД и NATS снаружи недоступны. Публичный стенд использует HTTPS; сервер и домен
будут выбраны позже. Локальная production-сборка не доказывает внешний деплой.

Основой HTTP-контрактов служат существующие модели React и типизированный
клиент: [контракт интеграции](../implementation/gateway-contract.md).
Публичные DTO используют camelCase; преобразование внутренних полей явное.
Документы геометрии не подвергаются рекурсивному переименованию ключей.
Строковые идентификаторы конструктора сохраняются и не обязаны быть UUID.

| Группа                | Назначение                                                                   |
| --------------------- | ---------------------------------------------------------------------------- |
| `/api/auth`           | Вход, refresh, сессия/текущий пользователь, выход, смена своего пароля       |
| `/api/users`          | Административные список, создание, изменение и сброс пароля                  |
| `/api/offices`        | Доступные здания и их документы; административные создание, настройки и план |
| `/api/booking/policy` | Зона времени, шаг, горизонт, серверное время и допустимые даты               |
| `/api/bootstrap`      | Сборка auth, доступных офисов и политики без зависимости от AI               |

Для бронирования нужны чтение занятости/своих броней, создание, изменение
и отмена одной брони; для администратора — управление чужими бронями.
Для чата — актуальное состояние, отправка сообщения, новый диалог, список
архива и чтение выбранного диалога. Точные новые URL/OpenAPI-схемы фиксируются
при реализации; массовая замена массива броней не является серверной операцией.

Передаются только разрешённые данные. Клиентская модель времени сохраняет
`date + start/end` в минутах московских суток; ограничения приходят с сервера.
Бронь содержит ID ресурса/здания, интервал, владельца, число участников комнаты,
состояние и пометку пересмотра. Имя/фамилия владельца доступны сотрудникам
в разрешённом здании. Публичный контракт не раскрывает внутренние DTO сервисов.

## 3. Вход и веб-сессия

1. Пользователь вводит логин и пароль в нашей форме. Саморегистрации и email нет.
2. Gateway передаёт проверку Users через NATS, получает выданные им полномочия
   и устанавливает HttpOnly cookies. Токены не возвращаются в JSON фронтенду.
3. Access JWT живёт 120 секунд. Подпись, issuer, audience, срок и обязательные
   claims проверяются Gateway локально, без Users/NATS на каждом запросе.
4. Refresh обращается к Users. Пока сессия разрешена, JWT обновляется незаметно.
   Выхода только из-за возраста сессии нет; предел в 30 дней отменён D-123.
5. Выход отзывает соответствующую сессию и очищает cookies.
   Отключение аккаунта и смена/сброс пароля отзывают сессии по ТЗ Users.

Подписанный контекст содержит устойчивый ID пользователя, ID сессии, роль
и назначенный доступ, временные и проверочные claims. Криптографические
параметры и хранение refresh принадлежат Users. Cookies в production Secure;
изменяющие запросы защищены от CSRF, в том числе проверкой допустимого Origin.
Внешние служебные заголовки не принимаются как контекст пользователя.

При отключении аккаунта согласовано окно действия выданного веб-JWT до
истечения. Постоянная проверка Users на горячем пути не требуется;
Redis/blacklist не являются обязательной зависимостью — D-116/D-117.
Поведение уже выданных JWT при смене пароля, роли/доступа, открытого SSE
и начатых операций ещё конкретизируется в Q-14. Отзыв refresh и запись
новых прав не откладываются. Мгновенный отзыв всех коротких токенов нельзя
заявлять без соответствующего механизма.

## 4. Авторизация и объектные права

Все проверки прав выполняет Gateway — D-117. Users хранит источник прав;
Booking сообщает факты о ресурсе/броне и исполняет разрешённую команду.
В Booking не добавляются копии пользователей, ролей или состояния их отзыва.

| Субъект                     | Доступ                                                                            |
| --------------------------- | --------------------------------------------------------------------------------- |
| Не вошедший                 | Форма входа и необходимые endpoints начала авторизации                            |
| Сотрудник                   | Назначенные здания, все ресурсы внутри, занятость и доступная собственная история |
| Сотрудник при записи        | Создание своей брони, изменение/отмена своих броней по правилам Booking           |
| Администратор через админку | Сотрудники, доступ, здания, планы, графики и все брони                            |
| MCP-клиент                  | Операции сотрудника и его права, без административных инструментов                |

Владелец определяется проверенным контекстом. `userId`, имя, роль и здания
из URL, тела запроса, промпта или аргумента инструмента не дают полномочий.
Для изменения Gateway получает факты о броне, проверяет владельца и здание;
для переноса — также целевой ресурс. Бизнес-переход проверяет Booking.

Неназначенные здания скрыты из списка, планов, поиска, броней и MCP.
После отзыва пользователь не видит даже свою историю этого здания; она
сохраняется для администратора. Отзыв одного здания не лишает остальных.
Границы видимости распространяются на push-события. Административная роль
не добавляет инструменты админки в MCP.

## 5. Общий MCP

Публичный удалённый MCP и MCP встроенного Assistant используют один контракт
к операциям клиентского бэка. Встроенный вызов может идти по внутреннему адресу
того же входа. Привилегированного обхода Gateway у Assistant нет.

Для внешнего клиента принят OAuth 2.1 Authorization Code + PKCE — D-115.
Gateway публикует необходимые discovery-метаданные и проверяет полномочия,
предназначенные для MCP-ресурса; Users владеет выдачей/отзывом. Пароль вводится
в нашей системе. Веб-cookie и двухминутный цикл не переносятся автоматически
на внешнюю MCP-авторизацию.

Клиентские операции: доступный каталог/планы/оснащение, временная политика,
поиск и занятость, свои доступные брони/история, подготовка новой брони,
клиентское управление своей бронью. При каждом вызове проверяются те же права,
что у HTTP. Список инструментов не заменяет проверку фактического вызова.
Переиспользование соединений/MCP-сессий не смешивает пользователей.

Создание требует подтверждения точных параметров в нашей форме, в том числе
для внешнего агента. Вызов модели или текст «подтверждаю» во внешнем чате
не является подтверждением в обход формы. Ограниченный набор инструментов
встроенного помощника описан в ТЗ Assistant и не урезает общий MCP-контракт.

Версия SDK/протокола, целевые клиенты, регистрация, формат/срок MCP-токенов,
refresh и делегирование проверяются при интеграции. Используются готовые
стандартные компоненты, собственный протокол не разрабатывается.

## 6. Ссылка и подтверждение формы

Предложение содержит параметры предзаполнения в URL: ресурс/здание, дату,
время и число участников, когда нужно. Изменение схемы сохраняет совместимость
или использует версию. Ссылка не имеет TTL, не создаёт запись предложения в БД
и пригодна для закладки — D-118.

По D-128 внешний MCP явно инструктирует агента показать url результата
prepare_booking как ссылку на нашу форму подтверждения. Во встроенном UI
структурированный proposal открывает ту же форму непосредственно; message
не печатает сырой URL. Поле proposal.url и общий MCP-контракт сохраняются,
подтверждение и права не зависят от способа открытия.

После входа пользователь возвращается к нашей форме с теми же параметрами;
возврат разрешён только на внутренний маршрут. Прошедшая дата оставляет поле
даты пустым, прочие параметры сохраняются — D-119. Недоступный/удалённый
ресурс обрабатывается явно, без подстановки другого. Параметры можно исправить
до подтверждения. Ссылка не удерживает ресурс, не задаёт владельца и прав.

При сохранении Gateway проверяет пользователя/права, Booking — текущие
условия. Клиент передаёт устойчивый `Idempotency-Key` одной отправки,
сохраняемый с бронью. Повтор после потери ответа возвращает тот же результат,
новая намеренная отправка получает новый ключ. Изменённые параметры с прежним
ключом дают ошибку несоответствия, а не вторую бронь. Повтор не должен
конфликтовать с бронью, созданной тем же подтверждением; актуальный доступ
всё равно проверяется. Ключ операции отличается от `requestId` и `traceId`.

Результат показывается в нашем UI. Callback во внешний чат не нужен;
внешний клиент при необходимости выполняет следующий MCP-запрос.

## 7. Внутреннее взаимодействие

Обычные вызовы Gateway → Users/Booking/Assistant идут через Core NATS
request/reply, а не внутренний HTTP — D-124. Assistant → Gateway сохраняет
HTTP MCP, OpenRouter — свой HTTP API.

Контракт несёт версию, действие, payload, удостоверенный контекст,
`requestId`/`traceId`, при необходимости — ключ операции. Доверие обеспечивают
служебные полномочия и ограничения брокера: публичный клиент не публикует
внутренние команды. Сервисы проверяют происхождение вызова, не повторяя
авторизацию пользователя. Subjects, queue groups, envelope, Python-обвязка
и тайм-ауты фиксируются при реализации; FastStream пока не выбран.

Надёжные фоновые команды/события используют JetStream и transactional outbox
сервиса-владельца — D-111/D-112. RPC/reply subjects не включаются в сохраняемые
потоки. Потребитель подтверждает сообщение после commit; повторы безопасны.
Gateway не становится outbox-БД.

Тайм-аут RPC не означает, что записи не было. Создание повторяется с тем же
ключом; для прочих изменений нужен безопасный повтор/чтение состояния.
Нельзя слепо повторять запись как новую операцию. Корреляция передаётся через
вызовы и события без записи секретов в логи.

## 8. SSE и восстановление

Бронирование и общий чат обновляются авторизованным SSE без long polling.
Gateway фильтрует аудиторию: разрешённое здание для плана/броней, конкретный
пользователь для диалога и архива. Изменения публикуются после сохранения.

Событие содержит идентификатор, тип, объект/область, версию состояния и данные
или указание перечитать снимок. Нужны обновления создания/изменения/отмены,
связанных комнаты/мест, сообщения/обработки чата и его архивирования.
Точные имена событий фиксируются в общем контракте.

После переподключения клиент получает актуальный снимок, а не все пропущенные
события — D-110. Переход снимок → поток не теряет изменений: потребление или
буферизация согласуются со снимком/ревизией. Повторы и поздние события
не откатывают UI. После восстановления брокера/подписки Gateway инициирует
повторную синхронизацию; потеря Core-события не оставляет экран устаревшим.

Короткий JWT не превращается в бессрочное разрешение потока: контракт задаёт
обновление авторизации/переподключение и отзыв по Q-14. В UI виден статус связи,
введённые поля сохраняются. Прокси не буферизует SSE. При исправной связи цель —
обновление других клиентов в пределах пары секунд; условия измерения
фиксируются в проверке, это не гарантия при обрыве сети.

## 9. Ошибки и независимость от AI

Ошибка содержит `code`, понятное `message`, `requestId`, при ошибках полей —
`fields`. Traceback, токены и пароли не выдаются. Различаются отсутствие входа,
недостаточные права/скрытый объект, валидация, конфликт занятости,
недоступная зависимость и неопределённый исход записи после тайм-аута.
Скрытый офис не раскрывается деталями ошибки.

Отказ Users запрещает новый вход/refresh, но не отменяет сам по себе
действующий локально проверенный JWT. Отказ Booking не выдаёт успешную бронь.
Отказ Assistant/OpenRouter/MCP помощника оставляет каталог, занятость
и ручную форму независимыми от AI. Этот путь не ждёт запуска Assistant.

## 10. Приёмка

- Действующий JWT проверяется без Users/NATS introspection, refresh обращается
  к Users. Вход не прекращается по возрасту сессии.
- Неверная подпись/audience/срок отклоняются; внешний контекст не позволяет
  подменить пользователя, его роль или назначенные здания.
- Сотрудник не читает скрытые здания, чужой чат/историю недоступного здания
  и не меняет чужую бронь. Админка и MCP проверяются раздельно.
- HTTP и MCP дают одинаковые клиентские права; OAuth внешнего и делегированный
  встроенный вызов проверены на двух пользователях.
- URL работает при повторном открытии, после входа и с прошедшей датой;
  до формы бронь не создаётся, текущие правила не обходятся.
- Потерянный ответ и повтор ключа возвращают ту же бронь; изменённое тело
  с прежним ключом отклоняется.
- Два клиента получают обновления карты/Ганта и общего чата; обрыв, повторы
  и поздние события восстанавливают актуальный снимок.
- Проверены RPC, недоступный сервис, тайм-аут с возможным commit и надёжное
  фоновое действие при недоступном Booking без ложного успеха.
- При отказе LLM/Assistant ручная форма остаётся работоспособной.

Проверки запускаются только в Docker на изолированном стенде.
Общие материалы сдачи — в [индексе документации](../README.md).
