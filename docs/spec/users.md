# ТЗ: Users

**Статус:** требования к целевому сервису, актуализированы 12.11.2026.
Документ описывает требуемое поведение, а не подтверждает готовность реализации.

Основания: [исходное задание](../source/assignment.md),
[журнал решений](../decisions.md), [архитектура](../architecture.md).
Публичные маршруты и браузерный контракт принадлежат [Gateway](gateway.md),
работа с бронями — [Booking](booking.md), интерфейс — [Frontend](frontend.md).
Текущее состояние серверного слоя описано отдельно в
[backend-foundation](../implementation/backend-foundation.md) и
[gateway-contract](../implementation/gateway-contract.md).

## 1. Назначение и границы

Users — независимо развёртываемый Python/FastAPI-сервис учётных записей,
паролей, ролей, назначенного доступа к зданиям и пользовательских сессий.
Он является источником этих данных, выдаёт и отзывает полномочия — D-109.

Gateway выполняет всю авторизацию: проверяет вход, роль, доступ к зданию,
владение конкретной бронью и допустимость публичной операции — D-117.
Users проверяет пароль, действительность принадлежащих ему сессий и
целостность своих данных. Это не означает обращения к Users для проверки
каждого обычного запроса.

Users не хранит планы, ресурсы, брони или переписку. Он не читает чужие
таблицы и не меняет бронь напрямую. Booking получает разрешённые команды
и необходимые бизнес-действия, но не копию учётных записей, ролей или
списков доступных зданий. Отдельной учётной записи для встроенного
помощника нет.

## 2. Владение данными

Данные находятся в отдельной БД Users одного экземпляра PostgreSQL,
со своими учётными данными и миграциями — D-113. Gateway собственной
БД сессий не имеет.

| Данные                | Обязательное содержание                                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Учётная запись        | Устойчивый ID, уникальный логин, имя, фамилия, хеш пароля, роль, признак активности, время создания и изменения           |
| Доступ к зданиям      | Набор устойчивых ID зданий, назначенный сотруднику администратором                                                        |
| Веб-сессия            | ID сессии и пользователя, проверочное значение refresh-токена, время создания, состояние отзыва и его причина             |
| Полномочия MCP        | Связь с пользователем и OAuth-клиентом, состояние выдачи/обновления/отзыва; authorization code и связанные данные PKCE    |
| Межсервисное действие | ID операции, причина и область отзыва, состояние выполнения отмены броней, результат или доступная для диагностики ошибка |
| Outbox                | Устойчивый ID события, тип и версия, данные, время возникновения, корреляция, состояние публикации                        |

Отключение учётной записи реализуется сохранением записи с `active=false`,
а не удалением ID, на который ссылается история. Изменение имени или логина
не создаёт нового владельца. Совпадение имени и фамилии не объединяет
сотрудников.

Логин нормализуется единообразно при создании, редактировании и входе:
пробелы по краям удаляются, регистр не различается. Уникальность обеспечивается
хранилищем, в том числе при конкурентном создании. Отключённая запись
сохраняет свой ID и логин. Дубликат отклоняется без частичного сохранения.
Имена и фамилии обязательны; email и контактные поля не требуются.

Пароль хранится только как стойкий проверочный хеш. Пароли, refresh-токены,
authorization code и ключи подписи не возвращаются в профилях, не передаются
LLM и не попадают в журналы. Для случайных непрозрачных токенов в БД
хранится проверочное значение, достаточное для проверки и отзыва.
Точные ограничения полей и политика паролей едины в схемах Users,
публичном контракте Gateway и формах; скрытые дополнительные ограничения
на отдельном канале не допускаются.

## 3. Учётные записи и административные операции

Сервис внутренний: самостоятельной регистрации нет. Администратор
создаёт пользователя, задавая логин, начальный пароль, имя, фамилию,
роль и список доступных зданий. Поддерживаются роли `employee` и `admin`.
Сотрудник без назначенных зданий имеет пустой доступ к каталогу;
создание нового здания не назначает его всем автоматически.

Администратор через Gateway может:

- получить список учётных записей и их состояние;
- создать запись, изменить логин, имя, фамилию, роль и набор зданий;
- сбросить пароль;
- отключить сотрудника с прекращением доступа и освобождением его броней.

Администратор управляет всеми зданиями по D-042/D-085. Набор зданий
сотрудника не ограничивает административные операции этой роли.
Отдельная функция временной блокировки с таймером не вводится.

Первый администратор создаётся отдельной явной bootstrap-командой внутри
Docker с переданным оператором паролем. Публичного маршрута для назначения
себе административной роли нет. Повтор bootstrap не меняет существующий
пароль и профиль. Установочного общего пароля в production нет.
Процедура запуска и имена переменных описываются в README.

## 4. Сценарии сотрудника

1. Вход через нашу форму по логину и паролю без email — D-003.
   Users проверяет учётные данные и активность, создаёт веб-сессию
   и выдаёт данные для короткого access JWT и refresh.
2. Повторное посещение восстанавливает разрешённую веб-сессию без
   периодического повторного ввода пароля — D-123.
3. Явный выход отзывает текущую веб-сессию. Выход из одного браузера
   сам по себе не является командой завершить все сессии пользователя.
4. Самостоятельная смена пароля требует текущий пароль. Изменяется
   проверочное значение и отзываются все сессии этого пользователя,
   включая текущую и MCP; продолжение требует нового входа — D-092.
5. Забытый пароль сбрасывает администратор, без email-восстановления.
   Сброс также отзывает все веб- и MCP-сессии пользователя.

Неверный текущий пароль не меняет пароль и сессии. Ошибка входа не создаёт
сессию. Отключённая запись не может войти или обновить полномочия.
Сессии и пароль другого пользователя не затрагиваются.

## 5. Доступ к зданиям и видимость истории

Администратор явно назначает сотруднику здания — D-085. Внутри назначенного
здания доступны все этажи и ресурсы; отдельные области доступа внутри
здания в текущий объём не входят.

Users хранит назначения по ID. Gateway получает необходимые факты
о зданиях из Booking и проверяет назначения и целевые объекты.
Сотрудник не получает скрытые здания, их планы, занятость или историю
через HTTP, SSE либо MCP. Владение старой бронью не даёт исключения
из актуальных прав — D-100.

При отзыве одного здания отменяются будущие брони пользователя в этом
здании, начавшиеся прекращаются и освобождают остаток интервала — D-089.
Брони в остальных зданиях не меняются. При отключении учётной записи
это действие распространяется на все её здания.

Прошедшая история и ссылки на владельца сохраняются. После отзыва здания
сотрудник не видит даже свою историю этого здания; после отключения
записи он полностью теряет доступ. Администратор сохраняет доступ
к историческим данным в пределах своей роли.

## 6. Веб-сессии и короткий JWT

Для веба принят подписанный access JWT со сроком **120 секунд** — D-116.
Gateway проверяет его подпись, издателя, аудиторию и срок локально;
обычный запрос плана, доступности или брони не вызывает Users для
проверки сессии. Users вызывается при входе, refresh и собственных
операциях домена пользователей.

JWT содержит идентификаторы пользователя и сессии, роль, назначенные здания,
время выдачи и окончания, издателя и аудиторию. Пользователь не задаёт
эти claims через форму. При refresh Users заново проверяет активность
записи и состояние сессии и выдаёт контекст с актуальными назначениями.
Ключи проверки получают только необходимые сервисы; остальные сервисы
не превращаются в самостоятельные точки пользовательской авторизации.

Refresh-сессия хранится Users и не имеет календарного предела вроде
30 дней. Возраст разрешённой сессии сам по себе не требует повторного
входа — D-123. Браузерное хранение и доставка токенов принадлежат Gateway:
HttpOnly cookies, Secure в production, защита изменяющих запросов
при использовании cookies. Токены не возвращаются React как поля профиля.

Отзыв прекращает вход и refresh сразу после фиксации в Users.
При отключении аккаунта уже выданный JWT может действовать до окончания
его короткого срока: это явно принятый компромисс D-116/D-117.
Проекция отозванных пользователей в Booking отвергнута. Redis или иной
кэш отзыва в Gateway не является обязательной зависимостью.

Причины отзыва при смене/сбросе пароля остаются обязательными, но точное
допустимое окно уже выданного JWT для этих причин, изменения роли и отзыва
здания отдельно не согласовано. Оно должно быть единообразно определено
в контракте Gateway вместе с открытым SSE и уже начатой операцией;
разрешение задержки при отключении аккаунта не выдаётся за такое решение.
Текущая реализация описана в implementation-документах и не заменяет
это согласование.

## 7. OAuth и MCP

Для внешнего MCP **выбран** OAuth 2.1 Authorization Code + PKCE — D-115.
Протокол не является кандидатом и повторного выбора не требует.
Публичные OAuth/MCP-маршруты предоставляет Gateway, состояние выдачи
и отзыва и связь с учётной записью принадлежат Users.

Пользователь вводит логин и пароль только в нашей системе. OAuth-клиент
получает полномочия для MCP-ресурса от имени этой же учётной записи.
Веб-cookie и двухминутный срок веб-JWT автоматически не переносятся на MCP.
Нужны стандартные метаданные обнаружения и проверенная совместимость
с выбранным внешним клиентом.

MCP предоставляет операции клиентского бэка сотрудника с теми же правами;
административных MCP-инструментов в текущем объёме нет — D-103.
Ограничение списка инструментов не заменяет проверку прав при исполнении.
Встроенный Assistant использует делегированные полномочия пользователя
для того же MCP-входа, без отдельного логина и привилегированного обхода.
Пароль и полномочия не являются текстом промпта или свободно выбираемым
аргументом модели.

Формат MCP-токенов, срок действия, refresh, регистрация клиентов,
детали делегирования и механизм отзыва конкретизируются совместно
с Gateway при интеграции. Отзыв всех сессий по D-092 включает и этот канал.

## 8. Взаимодействие и надёжные действия

Обычные внутренние операции Gateway → Users выполняются через
**Core NATS request/reply** — D-124. Набор операций:

| Группа                | Операции и результат                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------------- |
| Вход                  | Проверка логина/пароля, создание сессии, refresh, текущие данные профиля, отзыв текущей сессии              |
| Пароль                | Собственная смена с проверкой текущего пароля; административный сброс                                       |
| Учётные записи        | Список, создание, изменение профиля/роли/активности/назначений                                              |
| OAuth                 | Подготовка и обмен authorization code, выдача/обновление/отзыв полномочий по согласованному OAuth-контракту |
| Межсервисное действие | Получение состояния отзыва и вызванной им отмены броней                                                     |

Внутренние запросы принимаются только от доверенных сервисов.
Контекст исполнителя создаёт Gateway; внешние служебные заголовки
не дают права подменить пользователя. Ошибки имеют машинный код
и корреляцию запроса, не содержат секретов. HTTP-коды и публичные DTO
формирует Gateway. Тайм-аут ответа не объявляется доказательством,
что изменяющая операция не выполнялась.

Отзыв доступа и требуемая отмена броней сохраняются одной локальной
транзакцией: изменение Users, состояние административного действия
и outbox-запись — D-111/D-112. Публикация выполняется в JetStream;
запись отмечается отправленной после подтверждения брокера. Повтор
использует тот же ID события. RPC- и reply-subjects не попадают
в сохраняемые потоки.

Событие содержит ID операции и пользователя, область отзыва
(конкретные здания либо все), причину, время возникновения и корреляцию.
Booking исполняет отмену как бизнес-действие и сохраняет результат
до подтверждения доставки. Повторы события не создают новые действия
над уже обработанными бронями. Результат возвращается надёжно и
позволяет завершить административную операцию.

Если Booking недоступен, отзыв в Users сохраняется, задача не теряется,
а администратор видит состояние ожидания/ошибки выполнения отмены.
Ответ об успешной записи профиля не означает, что связанные отмены
уже закончены. После восстановления обработка продолжается безопасно.
Служебное состояние не является новой функцией временной блокировки.

## 9. Критерии приёмки

1. Только администратор создаёт пользователей и меняет чужие профиль,
   роль, доступ или пароль. Самостоятельной регистрации и email-полей нет.
2. Устойчивая идентичность сохраняется после переименования и отключения.
   Одинаковые имена допустимы, одинаковые нормализованные логины — нет;
   конкурентная попытка не создаёт дубликаты.
3. Пользователь входит, восстанавливает веб-сессию и выходит. Возраст
   сессии не вызывает плановый повторный вход; access JWT остаётся коротким.
   Обычный защищённый запрос проверяется Gateway без Users-introspection.
4. Смена и сброс пароля отзывают все серверные веб- и MCP-сессии только
   целевого пользователя. Старый refresh больше не выдаёт полномочия,
   новый пароль позволяет новый вход. Неверный текущий пароль ничего не меняет.
5. Сотрудник без назначений не видит зданий. Назначение открывает только
   соответствующие здания во всех каналах; запрос чужого ID не обходит Gateway.
6. Отзыв одного здания отменяет будущие и завершает текущие брони только
   этого здания. Отключение пользователя распространяется на все здания;
   прошлые данные и ссылки на владельца сохраняются.
7. После отзыва данные здания, включая собственную историю, скрыты от
   сотрудника. Отключённая запись не входит и не обновляет полномочия.
   Принятое окно старого веб-JWT при отключении проверяется отдельно.
8. Сбой между commit и публикацией не теряет отмену броней. Сбой Booking,
   повтор публикации, повтор доставки и потеря подтверждения не дают
   ложного завершения и не повреждают историю; администратор видит состояние.
9. Внешний MCP проходит выбранный OAuth-поток, использует собственные
   полномочия пользователя и не получает административные инструменты.
   Встроенный помощник не использует отдельную привилегированную запись.
10. Перезапуск сохраняет учётные записи, назначения, сессии, отзыв и outbox.
    Секреты отсутствуют в профилях, сообщениях модели и журналах.

Проверки с реальной БД и NATS выполняются в отдельном тестовом Docker-стенде,
без обращения к dev/prod данным. Подтверждение реализации и результаты
команд хранятся отдельно от этого ТЗ.

## 10. Оставшаяся техническая конкретизация

- Окно применения смены пароля, роли и доступа к зданию для уже выданного
  JWT; прекращение открытых SSE и граница уже начатых операций — Q-14.
- Точные OAuth/MCP-токены и параметры совместимости внешнего клиента;
  двухминутная веб-схема не считается их настройкой.
- Версионируемые NATS subjects/конверты, параметры повторов и контракт
  результата административной операции; выбор Python-обвязки — Q-12/Q-14.
- Поля, ограничения и криптографические параметры должны быть закреплены
  в схемах и конфигурации при реализации; новых продуктовых функций
  эти уточнения сами по себе не добавляют.
