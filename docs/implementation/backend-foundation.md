# Бэкенд и контейнеры

Этот файл фиксирует первоначальный этап каркаса и его проверки. После него
добавлены HTTP-брони, ревизии/импорт, SSE, OAuth/MCP, генерация Assistant и
Core NATS. Актуальное состояние и результаты: [gateway-contract](gateway-contract.md),
[backend-handoff](backend-handoff.md), [service-rpc](service-rpc.md).
Таблица из 87 тестов ниже относится к первоначальному этапу.

Дата: 12.11.2026. Это первый рабочий серверный слой, а не готовая реализация
всего тестового задания. Бизнес-основания: D-014, D-109, D-111–D-117, D-123.
Актуальный публичный контракт и решения BE-006–BE-009 описаны
в [Gateway для фронта](gateway-contract.md).

## Два варианта приложения

|           | Разработка                                                 | Production                                              |
| --------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| Compose   | `compose.dev.yaml`                                         | `compose.prod.yaml`                                     |
| Запуск    | `make up`                                                  | `make prod-up`                                          |
| Python    | Один dev-образ со всеми workspace-пакетами и инструментами | Отдельный образ каждого сервиса, только его зависимости |
| Исходники | Bind mount, Uvicorn hot reload                             | Код внутри образа, без bind mount исходников            |
| Фронт     | Vite за Nginx, публичный порт 5178                         | Собранные файлы, Nginx, порт 8080                       |
| API       | Через тот же Nginx `/api/`, документация `/api/docs`       | Через Nginx `/api/`, Gateway без порта на хосте         |
| Настройки | Есть локальные значения по умолчанию, `.env` необязателен  | Секреты обязательны, пример `.env.prod.example`         |
| Данные    | Собственные PostgreSQL/NATS volumes                        | Другие PostgreSQL/NATS volumes                          |

Имена проектов `workplace-booking-dev` и `workplace-booking-prod` отделяют сети
и volumes. БД и NATS не публикуют порты на хост. В prod Python-процессы работают
от непривилегированного пользователя, с read-only корнем и временным `/tmp`.
PostgreSQL и NATS находятся во внутренней сети; приложения также имеют сеть
для исходящих запросов. Gateway не зависит от запуска Assistant.

## Разработка

Нужны Docker Engine, Docker Compose и, для коротких команд, Make.
Python, uv и Node на хосте не требуются.

```bash
make up
make ps
make logs
```

Первый запуск собирает образы, создаёт три БД с отдельными владельцами,
выполняет Alembic-миграции и запускает четыре API, frontend и три outbox-процесса.
Серверные пользователи и каталог автоматически не заполняются.

Создание первого серверного администратора:

```bash
BOOTSTRAP_ADMIN_PASSWORD='ваш-пароль-длиной-от-8-символов' make bootstrap
```

Можно задать `BOOTSTRAP_ADMIN_LOGIN`, `BOOTSTRAP_ADMIN_FIRST_NAME` и
`BOOTSTRAP_ADMIN_LAST_NAME`. Повтор не меняет существующую запись и её пароль.
Настройки можно хранить в игнорируемом `.env`, по образцу `.env.example`.

```bash
make lint
make test
make smoke
make shell
make down
```

`make down` останавливает контейнеры и сохраняет данные. Тесты используют
отдельный `compose.test.yaml` с tmpfs для БД и брокера; `scripts/test.sh`
убирает этот стенд после завершения. Они не получают адреса dev/prod БД.

После изменения зависимостей: `make lock`, затем `make up`. Обе операции
выполняют установку внутри Docker. `uv.lock` — единственный создаваемый на хосте
результат разрешения Python-зависимостей. Окружение находится в `/opt/venv`
образа, JS-зависимости и кэш Vite — внутри frontend-контейнера.
Bytecode Python и кэш pytest отключены. `AGENTS.md` закрепляет этот порядок.

В VS Code можно открыть `.devcontainer/devcontainer.json`: рабочая папка
`/workspace`, Python `/opt/venv/bin/python`. `.devcontainer` использует тот же
dev-compose. Для иных редакторов достаточно `make shell`.

## Production

```bash
cp .env.prod.example .env.prod
# Заполнить пароли БД и INTERNAL_API_KEY (не короче 24 символов).
# ALLOWED_ORIGINS — JSON-массив публичных HTTPS-адресов приложения.
make prod-config
make prod-up
make prod-bootstrap
```

Bootstrap требует `BOOTSTRAP_ADMIN_PASSWORD`; его можно задать в `.env.prod`
или переменной окружения на время команды. Изменение переменной пароля БД
не меняет уже созданную роль: SQL инициализации выполняется только на новом volume.

Production-порт по умолчанию `127.0.0.1:8080`. Внешний HTTPS-прокси направляет
трафик туда; `COOKIE_SECURE=true` установлен в compose. Публичный HTTPS-адрес
нужно включить в `ALLOWED_ORIGINS`. Сертификаты, DNS и внешний деплой этим
локальным этапом не настраивались.

```bash
docker compose --env-file .env.prod -f compose.prod.yaml ps
docker compose --env-file .env.prod -f compose.prod.yaml logs --tail=100
make prod-down
```

Исходники в prod не монтируются. Из конфигов с хоста читаются только SQL-инициализация
и настройки NATS; Nginx-конфиг включён в образ. Отдельные образы можно собирать
через `docker compose ... build users` и аналогично для остальных сервисов.
Python-зависимости закреплены `uv.lock`; образы инфраструктуры пока закреплены
тегами версий, не digest.

## Что уже работает

| Сервис     | Реализовано                                                                                                                                   |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Gateway    | DTO существующего фронта, агрегация bootstrap, локальная проверка JWT, все права, HttpOnly cookies, Origin и ошибки                           |
| Users      | Вход/выход, профиль, создание и изменение сотрудников администратором, смена и сброс пароля, отзыв всех сессий, назначенные здания, bootstrap |
| Booking    | Каталог, создание офиса, сохранение плана и настроек, проекции ресурсов, политика времени; права проверяет Gateway                            |
| Assistant  | Хранение диалогов/сообщений, один активный диалог, архив, изоляция истории, новый диалог, информация о настройке LLM                          |
| Общий слой | Конфигурация, внутренний ключ и доверенный контекст Gateway, JWT, request ID, liveness/readiness, outbox и публикация в JetStream             |

В каждой БД свой outbox. Изменение сотрудника или диалога и запись события
сохраняются одной транзакцией. Отдельный процесс публикует событие, сохраняет
подтверждение брокера и повторяет неудачу с тем же `Nats-Msg-Id`. Это подтверждение
публикации, а не выполнения действия другим сервисом. Потребители и отображение
завершения административной операции ещё не реализованы.

Refresh-сессии — случайные непрозрачные значения, в БД только SHA256 от токена.
Пароли проверяются Argon2id. По D-123 refresh-сессия не имеет календарного срока.
Users выдаёт короткий access JWT на 120 секунд, Gateway проверяет его локально.
Смена пароля и отключение запрещают refresh; выданный JWT может действовать
до своего истечения. Внутренние сервисы доверяют служебному контексту Gateway;
пользовательские заголовки внешнего клиента не удостоверяют личность.

## Начальные маршруты Gateway

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`.
- `POST /api/auth/password`.
- `GET/POST /api/users`, `PATCH /api/users/{id}`, `POST /api/users/{id}/password`.
- `GET /api/booking/policy`, `GET /api/buildings`.
- `GET/POST /api/offices`, `GET /api/offices/{id}`, отдельные команды `/settings` и `/plan`.
- `POST /api/auth/refresh`, `GET /api/auth/session`, `GET /api/bootstrap`.
- `GET /api/assistant/capabilities`, `GET /api/chats/current`, `GET /api/chats`,
  `GET /api/chats/{id}`, `POST /api/chats/new`.

Вход: JSON `{ "login": "admin", "password": "..." }`. Публичный ответ содержит
профиль и дату истечения; токен остаётся в HttpOnly cookie. Изменения с cookie
требуют допустимый `Origin`. Внутренний API недоступен через публичный Gateway.
Публичные DTO используют существующий camelCase фронта; внутренние поля
преобразует Gateway. Типизированный React-клиент добавлен, Providers пока локальные.
Общедоступных административных MCP-инструментов не добавлено.

## Следующий слой

Серверные создание/изменение/отмена броней, конкурентная защита комнаты и мест,
идемпотентное подтверждение и подключение Providers к серверу ещё впереди.
Текущее чтение каталога возвращает пустой список на чистой БД.
SSE, потребители JetStream, OAuth Authorization Code + PKCE и сам публичный MCP
пока не реализованы. Выбранный протокол D-115 не заменяется временной cookie-сессией.
Pydantic AI установлен; генерация, MCP-инструменты и вызовы OpenRouter не запущены.
Модель остаётся за пользователем; `generationAvailable=false` возвращается явно.

React продолжает пользоваться браузерными данными и демо-входом, независимо
от серверных пользователей. Локальный запуск production-образов не означает
готовность всего продукта или его публикацию в интернете.

## Решения реализации

- **BE-001 — uv workspace и четыре Python-пакета.** Общий lockfile даёт согласованные
  зависимости; prod устанавливает только выбранный пакет и его зависимости.
  Альтернатива: четыре requirements/lockfile с независимыми версиями общего слоя.
- **BE-002 — контейнеры для всех команд.** Прямое требование пользователя;
  зависимости и генерируемые файлы не засоряют хост. Альтернатива: локальные venv/npm.
  Dev и prod используют отдельные compose-файлы по прямому запросу пользователя.
- **BE-003 — первоначальная introspection через Users.** Заменена коротким JWT
  и проверками в Gateway по D-116/D-117 и BE-008. История решения сохранена;
  вызова Users для проверки каждого обычного HTTP-запроса теперь нет.
- **BE-004 — отдельные publisher-процессы.** API не держит фоновый ненадёжный
  publish после commit; сбой и повтор покрывает outbox. Альтернатива: publisher
  в lifespan каждого API-процесса. Обработчики downstream пока отсутствуют.
- **BE-005 — собственный временный test-compose.** Настоящие PostgreSQL и NATS,
  но тесты не меняют рабочие данные. Альтернативы: SQLite или общая dev-БД.

Практика контейнерной установки сверена с [uv Docker](https://docs.astral.sh/uv/guides/integration/docker/)
и [FastAPI Docker](https://fastapi.tiangolo.com/deployment/docker/).

В автотестах проверены отзыв нескольких сессий после смены пароля и отключения,
изменение доступа к зданиям, изоляция каталогов и истории диалогов, конкурентное
создание нового диалога, сохранение позднего ответа в архив, retry outbox с тем же
идентификатором и запрет чужому сервису подключаться к БД Users.
Обязательные тесты конкурентного **бронирования** и проверка отключения его защиты
будут добавлены вместе с реализацией записи броней.

Production-проверку повторяет `make prod-smoke`: он собирает образы и поднимает
отдельный `workplace-booking-prod-proof` с тестовыми учётными данными и случайным
локальным портом, затем удаляет его контейнеры, сети и данные. Реальный
production-проект и `.env.prod` не используются. Эта проверка подтверждает
работу образов локально, без внешнего TLS и без браузерной интеграции с API.
