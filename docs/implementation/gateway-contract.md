# Gateway и существующий фронт

12.11.2026. Публичный API строится от существующих `auth/types.ts`,
`auth/authModel.ts`, `model.ts` и `client/types.ts`. Внутренние DTO сервисов
не становятся контрактом React. Бизнес-правила по-прежнему определяются
принятыми решениями; особенности локального демо не переносятся на сервер.

## Единый вход

И dev, и prod публикуют только Nginx. Dev: `http://localhost:5178`;
prod: настроенный `HTTP_BIND:HTTP_PORT`, по умолчанию `127.0.0.1:8080`.

- `/` — React: Vite в dev, статические файлы в prod.
- `/api/` — Gateway, включая `/api/docs` и `/api/openapi.json`.
- `/mcp` — официальный MCP SDK Streamable HTTP с отдельными OAuth-полномочиями.
- `/oauth/*`, `/.well-known/*` — OAuth Authorization Code + PKCE и обнаружение MCP.
- `/health` — жив ли сам Nginx; `/internal/` снаружи возвращает 404.

Dev WebSocket Upgrade проксируется к Vite через тот же Nginx. Проксирование
API не буферизуется; установлен timeout 300 секунд для SSE и MCP.
JSON с растровыми подложками принимает Nginx с лимитом тела 32 MiB.
TLS завершается внешним HTTPS-прокси. Внутренние HTTP, PostgreSQL, NATS
и monitoring-порты не публикуются.

## Формы данных

| Фронт                  | Gateway                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `AppUser`              | `id, login, firstName, lastName, role, active, buildingIds, createdAt`                                                   |
| `AuthSnapshot`         | `user, users, expiresAt`; по D-123 срок `null` при активном пользователе, список пользователей только для администратора |
| `OfficeConfig`         | `version:1, id, revision, name, address?, updatedAt, floors, hours`                                                      |
| `Floor`, `PlanElement` | Геометрия, подложка, `resourceType`, `roomId`, `equipment`, `points`; расширенные поля сохраняются                       |
| Политика времени       | `timezone, stepMinutes, horizonDays, serverNow, earliestStart, allowedDates`                                             |
| Ошибка                 | `code, message, requestId`, при проверке полей также `fields:[{field,message}]`                                          |

Преобразования явные: например, `first_name` → `firstName`, `hours_document`
→ `hours`. Словари и документы плана не проходят рекурсивное переименование
ключей. Произвольные строковые ID сохраняются, включая префиксы конструктора;
публичные маршруты не требуют UUID. Неверная геометрия, дубликаты ID,
циклические связи помещений и неподдерживаемые подложки отклоняются до записи.

## Операции

| Маршрут                                                           | Назначение                                                                           |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `POST /api/auth/login`                                            | `{login,password}` → `AuthSnapshot`, HttpOnly cookies                                |
| `POST /api/auth/refresh`                                          | Обновить короткий access JWT по refresh-cookie                                       |
| `GET /api/auth/session`                                           | Собрать текущий `AuthSnapshot`                                                       |
| `GET /api/auth/me`                                                | Текущий `AppUser` из подписанного JWT                                                |
| `POST /api/auth/logout`                                           | Отозвать refresh-сессию, очистить cookies                                            |
| `POST /api/auth/password`                                         | Форма фронта `{current,password}` → команда Users                                    |
| `GET/POST /api/users`                                             | Административный список и создание, camelCase                                        |
| `PATCH /api/users/{id}`                                           | Полный `UserUpdate`, включая редактируемый логин                                     |
| `POST /api/users/{id}/password`                                   | Административный сброс `{password}`                                                  |
| `GET /api/offices`                                                | Полные документы доступных офисов                                                    |
| `GET /api/offices/{id}`                                           | Полный `OfficeConfig` одного офиса                                                   |
| `POST /api/offices`                                               | `{name,address?}` → новый офис с пустым этажом                                       |
| `PATCH /api/offices/{id}/settings`                                | `{name,address?,hours,revision}`; не перезаписывает план                             |
| `PUT /api/offices/{id}/plan`                                      | `{floors,revision}`; не перезаписывает настройки                                     |
| `POST /api/offices/import`                                        | `{document}`, Idempotency-Key; сохраняет ID и геометрию                              |
| `GET/POST /api/offices/{id}/bookings`                             | История/фильтры дат; создание одной брони с Idempotency-Key                          |
| `GET/PATCH /api/offices/{id}/bookings/{bookingId}`                | Чтение/изменение с revision либо If-Match                                            |
| `POST /api/offices/{id}/bookings/{bookingId}/cancel`              | Отмена/досрочное завершение с revision                                               |
| `GET /api/offices/{id}/availability`                              | Интервал/курсор, ресурсы и фактическая занятость                                     |
| `GET /api/events`                                                 | Один авторизованный поток изменений брони/плана/чата                                 |
| `GET /api/access-operations`, `GET /api/access-operations/{id}`   | Только администратор: результат фонового отзыва доступа                              |
| `GET /api/assistant/capabilities`                                 | Состояние настройки модели без ключей                                                |
| `GET /api/chats/current`, `GET /api/chats`, `GET /api/chats/{id}` | Общий активный диалог и архив сотрудника                                             |
| `POST /api/chats/new`                                             | Архивировать текущий и начать новый диалог                                           |
| `POST /api/chats/{id}/messages`                                   | Сообщение/контекст офиса + Idempotency-Key → 202 snapshot                            |
| `GET /api/generations/{id}`                                       | Состояние отправленного запроса, только его владелец                                 |
| `GET /api/booking/policy`                                         | Действующие параметры времени в форме для UI                                         |
| `GET /api/bootstrap`                                              | `{auth,offices,policy}`; независимые запросы собираются параллельно, AI не требуется |

Создание и изменение пользователей и офисов — административные операции.
Сотруднику показываются только назначенные здания; запрос скрытого офиса
возвращает 404 до обращения к Booking. У старых строк каталога без сохранённой
геометрии полный документ недоступен явно: `409 office_document_unavailable`;
фиктивный план не подставляется.

В Booking добавлена миграция `0002`: настоящее `updated_at`, исходное расписание
и поддержка ID конструктора. Документы этажей хранятся целиком; нормализованные
ресурсы обновляются в той же транзакции. Сохранение настроек и плана блокирует
строку соответствующего офиса, поэтому эти операции не теряют данные друг друга.
Удалённые из плана ресурсы сохраняются в каталоге с признаком удаления.
Каждое сохранение записывает outbox-событие атомарно.

## Авторизация

Реализованы D-116, D-117 и D-123. Users выдаёт HS256 access JWT на 120 секунд
и владеет случайной refresh-сессией без календарного срока. Gateway проверяет
подпись, issuer, audience и срок локально. Обычные чтения плана и политики
не вызывают Users для проверки полномочий. Users нужен при входе/обновлении
и для собственных доменных операций — например, списка сотрудников.

Ключ `WEB_JWT_SECRET` (минимум 32 символа) получают только Users и Gateway.
HttpOnly access-cookie имеет путь `/`, refresh-cookie — `/api/auth`.
В prod обе cookies Secure; изменения через cookies требуют допустимый Origin.
Refresh-cookie продлевается при обновлении в пределах политики хранения браузера;
на сервере календарного предела сессии нет. Миграция Users `0002_unlimited_refresh`
снимает прежний срок у неотозванных сессий, сохраняя историю уже отозванных.
Токены не возвращаются в JSON фронту. После отзыва, выхода или смены пароля
refresh больше не работает; ранее выданный access JWT может действовать
до конца своих 120 секунд. Отдельный blacklist/Redis не добавлен.

Роль, доступ к зданию и разрешение публичной операции проверяет Gateway.
Внутренние сервисы проверяют служебный ключ и исполняют разрешённые команды;
повторного HTTP-запроса introspection из Booking или Assistant нет. Users хранит
сами права и состояние учётной записи, Booking — факты пространства и инварианты.
Служебные заголовки внешнего запроса не принимаются как контекст пользователя.
Веб-JWT не используется как внешняя MCP-авторизация. Users хранит стандартные
OAuth-клиенты, коды и токены через официальный MCP provider. Отдельный
`MCP_ENCRYPTION_KEY` защищает recoverable client secret; токены/коды хранятся
как хеши. Доступ привязан к ресурсу `${PUBLIC_BASE_URL}/mcp` и сессии Users.
Для каждого вызова Gateway проверяет MCP-токен через Users по Core NATS.
Обычные веб-запросы по-прежнему проверяют JWT локально.

Публичный OAuth-прокси допускает только известные SDK endpoints. Произвольный
путь не становится вызовом приватного обработчика, даже после URL-нормализации.
Origin-политику веб-cookie API сохраняем; публичный CORS OAuth обслуживает SDK.

## Подключение React

`src/shared/api/client.ts` импортирует существующие типы фронта. Один экземпляр
`GatewayClient` используется всеми Providers: это объединяет параллельные
обновления JWT в один запрос. Запросы идут на относительный `/api` с cookies;
после истечения access выполняются один refresh и одна повторная попытка.
Окончательный 401 при восстановлении сессии даёт пустой `AuthSnapshot`.

Providers подключены отдельным фронтовым чатом. План переносится явным импортом
через API, старый браузерный архив сохранён. Брони/пользователи автоматически
не переназначаются текущему администратору и не импортируются из localStorage.

Для `ClientBooking` сохранена форма `date + start/end` в минутах, строковые ID
и `ownerName`; добавлены revision и needsReview. Команды изменяют одну бронь
с серверной проверкой. Имя владельца склеивает Gateway по Users; владелец
сотрудника определяется контекстом. HTTP администратор получает внутренний
режим administrative, MCP — только собственные изменения без этого режима.

## MCP и помощник

Инструменты: list_offices, get_office, list_bookings, availability, prepare_booking,
update_booking, cancel_booking. Административных инструментов и прямого создания
брони нет. Built-in Assistant видит только первые пять инструментов по D-043.
Каждый LLM-запуск получает новую делегацию пользователя/веб-сессии и отдельный
HTTP/MCP-клиент. Полные картинки и расширенные поля плана в LLM не передаются;
отдаём данные ресурсов, оснащение и геометрию окружения.

prepare_booking возвращает `{proposal,url}` с канонической ссылкой
`/booking?officeId=…&floorId=…&resourceId=…&date=…&start=…&end=…&participants=…`.
Необязательные поля пропускаются; прошедшая дата очищается, время сохраняется.
Это предзаполнение, бронь появляется только после подтверждения нашей формы.
URL не удерживает ресурс и не задаёт владельца.

Запрос генерации выполняется durable worker; POST и GET возвращают одинаковый
`{request,session,messages}` со snake_case полями Assistant. Proposal остаётся
в сообщении и восстанавливается при открытии истории. SSE сигнализирует о
необходимости перечитать снимок. Без OPENROUTER_MODEL/API_KEY отправка даёт
503 assistant_unconfigured, capabilities — generationAvailable=false.

Детальные примеры для фронта: [backend-handoff](backend-handoff.md).

## Решения и альтернативы

- **BE-006 — BFF по моделям фронта.** Прямой запрос пользователя. Gateway
  собирает нужные UI документы и переводит внутренние поля явно. Альтернативы:
  заставить React знать схемы каждого сервиса; рекурсивно переименовывать весь JSON.
- **BE-007 — настройки и план отдельными командами.** Соответствует двум
  редакторам фронта и сохраняет параллельные изменения. Альтернатива: перезапись
  полного офисного документа каждым экраном с риском потерять чужой блок данных.
- **BE-008 — короткий веб-JWT, права в Gateway.** Реализация D-116/D-117,
  заменяет первоначальную introspection каждого HTTP-запроса из BE-003.
  Альтернатива с немедленным отзывом требует дополнительного состояния;
  пользователь разрешил короткое окно и не выбрал Redis обязательной частью.
- **BE-009 — один Nginx в обоих Compose.** Прямой запрос пользователя.
  UI, API и HMR имеют одну origin; отдельные публичные порты Vite/Gateway убраны.
  Альтернатива: доступ к каждому процессу через собственный порт.
- **BE-010 — refresh без календарного истечения.** Реализация нового D-123,
  заменяет прежние фиксированные 30 дней. Альтернатива: продлевать срок от каждого
  входа/обновления; пользователь предпочёл выход только по отдельной причине.
  Двухминутный срок access JWT сохраняется.
- **BE-011 — официальный MCP SDK и единый employee facade.** SDK обслуживает
  Streamable HTTP, discovery, OAuth handlers и PKCE. Users реализует provider
  хранения и входа, Gateway повторно использует клиентские операции и ограничения.
  Альтернативы: собственный протокол MCP/OAuth; отдельный привилегированный бэк
  помощника. Оба варианта добавляли бы расходящиеся права и проверки.
- **BE-012 — внутренний транспорт Core NATS.** Реализация D-124 через общий
  ServiceTransport и существующие типизированные обработчики. Внешние HTTP,
  OAuth, MCP и SSE остаются стандартными публичными протоколами; за Gateway
  запросы/ответы сервисов идут через брокер, надёжные события — через JetStream.
  Подробности и альтернативы: [service-rpc](service-rpc.md).
- **BE-013 — отдельная проекция данных для LLM.** Передаём ресурс/оснащение и
  известные поля геометрии, включая вложенные equipment/points; расширения
  браузерного документа и растровые подложки сохраняются для UI. Альтернатива:
  отдавать модели полный OfficeConfig с base64 и произвольными расширениями.

Проверки выполняются в контейнерах. Бэкенд: `make test`, линтер: `make lint`;
frontend: `docker compose -f compose.dev.yaml run --rm --no-deps frontend npm test`.
`make smoke` проверяет dev ingress, Swagger/OpenAPI и реальный WebSocket Upgrade
для HMR. `make prod-smoke` поднимает отдельный временный production-стенд,
проверяет офис/план/пользователей через Nginx и передаёт документ настоящему
фронтовому `parseConfig` без промежуточного преобразования.

Полный серверный прогон 12.11.2026: **283 passed** на отдельном PostgreSQL/NATS.
После уточнения вложенной LLM-проекции и фильтра этажа дополнительно прошли
46 целевых Gateway-проверок. Ruff прошёл. Dev smoke подтвердил readiness,
Swagger/OpenAPI и WebSocket 101 через Nginx. Production smoke — отдельный
воспроизводимый стенд, без публичного домена/TLS и платного вызова OpenRouter;
Локальный production smoke от 12.11.2026 завершён с EXIT 0 на образах всех четырёх
сервисов: сверены установленные service/platform исходники, вход/права,
план/настройки/revision, OAuth PKCE → MCP каталог/частичное предложение,
обновление/отзыв токенов и настоящий frontend parseConfig. Проверочный клиент
делит network namespace единственного Nginx с issuer http://localhost:8080;
SDK-проверка HTTPS/loopback не отключалась. Временные контейнеры/volumes удалены,
dev-данные сохранены. Реальный LLM и публичный TLS этим прогоном не проверялись.
