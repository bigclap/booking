# Проверка границ Gateway

Дата: 12 ноября 2026 года. Проверялись OAuth-прокси, общий фасад HTTP/MCP,
передача пользовательского контекста, версии изменений, события чата и правила
Nginx. Команды выполнялись в Docker. Платных вызовов модели и обращений
к реальным внешним OAuth-клиентам не было.

## Публичный OAuth и доверенный RPC

До исправления публичный маршрут `/oauth/{path:path}` добавлял произвольный
остаток пути к адресу Users. HTTPX нормализовал `..` до проверки внутреннего
RPC-пути, а `ServiceTransport` добавлял служебный ключ для обращения к Users.

Воспроизведение в памяти, без настоящего NATS и чтения пользовательских данных:

```text
GET /oauth/%2e%2e/internal/users/sentinel
HTTP 200
recorded RPC path: /internal/users/sentinel
trusted_key_injected: True
```

Ответ содержал специально подготовленное тестовое значение. Это доказательство
ошибки на границе Gateway; доступность той же строки через Nginx отдельно
не доказывалась. Nginx может нормализовать и отклонить часть таких запросов,
но защита самого публичного прокси не должна от этого зависеть.

В [OAuth-прокси](../../apps/gateway/src/workplace_gateway/oauth_proxy.py)
до создания upstream URL проверяется закрытый список путей: `authorize`,
`login`, `token`, `register`, `revoke` и метаданные authorization server.
Произвольные вложенные и закодированные пути не выбирают внутренний обработчик.
Публичные заголовки идентификатора пользователя, сессии и доверенного контекста
не передаются. Служебный ключ для разрешённого RPC формирует сам транспорт.

## OAuth CORS

До исправления общий CORS Gateway отвечал `400 Disallowed CORS origin` на
preflight `/oauth/token` с `Origin: http://localhost:6274`, не передавая запрос
официальному SDK. Прокси также не передавал `Access-Control-Request-Method`
и `Access-Control-Request-Headers`.

Сейчас OAuth и метаданные используют CORS официальных OAuth-обработчиков.
Прокси сохраняет заголовки preflight. Ограничение origin для обычного
веб-интерфейса с cookie остаётся отдельным и проверяется регрессией.

## Воспроизводимые регрессии

[Набор тестов](../../apps/gateway/tests/test_gateway_oauth_security.py)
использует настоящий `ServiceTransport`, мост RPC в памяти и реальные CORS-
обработчики официального MCP SDK. PostgreSQL и платная модель ему не нужны.

```bash
docker compose -f compose.dev.yaml run --rm --no-deps dev \
  pytest -q apps/gateway/tests/test_gateway_oauth_security.py
```

Результат проверенного запуска: **9 passed in 2.35s**. Отдельная проверка
Ruff этого файла также прошла.

- Пять вариантов обхода пути возвращают `403`/`404` до любого RPC.
- Preflight token/register с внешнего origin доходит до SDK и получает CORS-ответ.
- Этот же origin не получает разрешение на веб-API с cookie.
- Метаданные сохраняют канонический issuer; свободно заданные actor headers
  не попадают во внутренний контекст.

Эти тесты не являются проверкой реального брокера или полного подключения
ChatGPT. Проверки настоящего NATS описаны отдельно в [документе RPC](service-rpc.md).

## Синхронизация архива чата

Обнаружено несовпадение контрактов: после создания брони Assistant отправляет
`session_id: null` вместе с `archived_session_id`, а Gateway отбрасывал событие
без непустого текущего session ID. Другие вкладки не получали `chat.changed`.

В текущем преобразователе событий допускается явный `null` текущего диалога,
если передан корректный ID архивированного. Отсутствующий или некорректный
контекст по-прежнему не считается допустимым событием. Этот сценарий не входит
в приведённые выше девять OAuth-тестов.

## Проекция плана в контекст модели

Одного `element.model_dump(include=<известные поля элемента>)` недостаточно:
вложенные `EquipmentItem` и `PointDocument` сохраняют дополнительные поля.
Проверка в Docker показала сохранение тестового `private_raster` с data URL
внутри `equipment[0]` и `points[0]`.

Для LLM нужна явная проекция: оснащение только `{type, quantity}`, точки
только `{x, y}` или их исключение из контекста. Полный документ для браузера
при этом должен продолжать сохранять расширения. Фасад исправлен: явные
resource_projection/scene_element удаляют также вложенные расширения.
Тест get_office содержит private_raster и в equipment, и в points; проверяет
их отсутствие в LLM-проекции при сохранении type/quantity и x/y.

## Предел размера RPC

На момент проверки [Nginx](../../infra/nginx/default.conf) принимает тело до
`32m`, а [NATS](../../infra/nats/nats.conf) имеет `max_payload: 16MB`.
В RPC передаётся envelope, поэтому полезный документ должен быть меньше
брокерного предела с запасом на служебные данные. Несколько встроенных растровых
подложек также увеличивают совокупный ответ списка офисов/bootstrap.

Это техническая граница транспорта, а не согласованная бизнес-квота.
Допуск Nginx не означает допуск RPC: большой документ/совокупный ответ
может получить контролируемый `413 rpc_payload_too_large`. Gateway возвращает
понятное сообщение о размере данных/подложек. Лимиты сейчас не являются
одинаковыми, и произвольный документ до 32 MiB не заявляется поддержанным.

В RPC есть предварительная проверка длины ответа и обработка SDK MaxPayloadError.
Сервисный чат проверил настоящий NATS с 16 MiB: запрос/ответ 1100 KiB проходит,
запрос 17 MiB получает 413 до handler, маленький запрос с результатом 17 MiB
получает короткий 413 без тайм-аута. Целевой тест прошёл за 1.50 s; подробности
в [service-rpc](service-rpc.md). Ошибка размера ответа не доказывает откат
уже завершённой записи: повтор создания использует прежний Idempotency-Key.
