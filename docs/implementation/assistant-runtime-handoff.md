# Контракт рантайма Assistant

`apps/assistant/src/workplace_assistant/runtime.py` — единый рантайм
Pydantic AI. `run_agent(settings, prompt, history, context, mcp_token)` возвращает
`RuntimeResult(reply, run_messages)`. Отдельного неиспользуемого рантайма нет.
Тесты явно подставляют `FunctionModel`; production использует только
`OpenRouterModel` с заданными `OPENROUTER_MODEL` и `OPENROUTER_API_KEY`.

Каждый запуск создаёт собственный HTTP-клиент, cookie jar и MCPToolset.
Токен передаётся transport-auth callback через `RuntimeDependencies`,
не в промпте/аргументах инструмента и не в сохраняемой SDK-истории.
`X-Request-ID`/`X-Trace-ID` берутся из текущего серверного контекста
корреляции и передаются MCP в заголовках, также вне промпта и SDK-истории.
В SDK V2 используется `MCPToolset`; удалённый `MCPServerStreamableHTTP`
и старый `mcp.server.fastmcp.FastMCP` не применяются.

## MCP-инструменты встроенного сценария

Текущий allowlist: `list_offices`, `get_office`, `list_bookings`,
`availability`, `prepare_booking`. Он фильтрует инструменты модели;
Gateway продолжает проверять настоящие права пользователя.
Инструменты создания, изменения, отмены брони и администрирования модели
не предоставляются. Общий внешний MCP этим ограничением не меняется.

После уточнения UX 12.11.2026 встроенный runtime просит модель дать короткое
описание места/этажа/времени без URL и Markdown-ссылок в `message`.
Ссылка остаётся в `proposal.url`; фронт открывает форму по структурированным
полям и оставляет кнопку повторного открытия. Это инструкция для будущих
ответов, не переписывание сохранённой истории и не изменение внешнего MCP.
В стороннем чате агент должен показать ссылку из результата `prepare_booking`
пользователю для перехода к подтверждению. Запрет печатать URL относится
только к `message` нашего встроенного Assistant; общий MCP продолжает
возвращать открываемый адрес формы.

`prepare_booking` возвращает структурированный результат:

```json
{
  "proposal": {
    "officeId": "office-id",
    "floorId": "floor-id",
    "resourceId": "resource-id",
    "date": "2026-11-12",
    "start": 600,
    "end": 660,
    "participants": 3
  },
  "url": "/booking?officeId=office-id&resourceId=resource-id&date=2026-11-12&start=600&end=660"
}
```

Время — минуты московского дня. Поддерживается также `url` внутри
`proposal` и JSON-текстовый ответ MCP SDK. Дата и время могут быть частично
заполнены по D-118/D-119; если заданы оба края, начало предшествует концу.
Разрешены относительная ссылка `/booking?...` и абсолютная ссылка на
`/booking` только с origin из серверного `PUBLIC_BASE_URL`. Credentials,
фрагмент и другой origin запрещены. Ошибка MCP или некорректный ответ
не становятся предложением.

Модель может вернуть только точные параметры успешного `prepare_booking`
из этого же запуска. Придуманное предложение вызывает конечный validation
retry; модель может ответить текстом без `proposal`. Эта проверка не удерживает
ресурс: правила и доступность снова проверяются при подтверждении формы.

## Выполнение и восстановление

`generation_worker.py` хранит запросы, захватывает SQL lease и сохраняет
ответ вместе с outbox-событием. Для каждого исполнения нужно заново получить
делегированные MCP-полномочия исходного пользователя и исходной веб-сессии.
Users должен отказать после отзыва этой сессии/аккаунта; сохранённые ID
сами по себе не являются полномочиями. Bearer в запросе генерации не хранится.
Для выдачи делегации worker использует `service_client`: при
`INTERNAL_RPC_ENABLED=true` запрос к Users идёт через Core NATS.
Внешний MCP остаётся HTTP.

Слот отправки общий для пользователя, включая незавершённый ответ уже
архивированного диалога. Создание нового диалога не разрешает второй
параллельный запуск. Снимки `GET /internal/chats/current`,
`GET /internal/chats/{id}` и результат «Нового диалога» дополнены полями:

- `request` — последний запуск выбранного диалога, включая ошибку;
- `processing` — текущий `pending/running` запуск пользователя, даже если
  он принадлежит уже архивному диалогу.

Это позволяет восстановить состояние после перезагрузки и обрыва SSE
без повторного вызова модели. Существующие `session` и `messages` сохранены.

История обрезается по целым завершённым SDK-запускам, поэтому вызовы
инструментов не отделяются от результатов. Число последних запусков и бюджет
в символах задаются `generation_history_runs`/`generation_history_chars`;
это не заявленный точный лимит токенизатора. Системные инструкции и текущий
запрос добавляются отдельно. Ограничены число запросов/инструментов, время,
повторы валидации и выходные токены. База сохраняет полную историю.

## Проверка

Исторические проверки от 12.11.2026 выполнялись в отдельном Docker-стенде:

```sh
docker compose -f compose.test.yaml run --rm --no-deps tests \
  pytest -q apps/assistant/tests/test_llm_runtime.py
```

Тест поднимает настоящий MCP Streamable HTTP endpoint на случайном loopback
порту внутри контейнера, выполняет параллельные Pydantic AI-запуски с разными
bearer, проверяет фильтр инструментов, grounding, конечный бюджет вызовов,
полные группы контекста и отсутствие credentials в сохраняемой истории.
Модель в этом тесте детерминированная. Это доказательство интеграции SDK/MCP,
а не выполненного платного запроса OpenRouter или проверки выбранной модели.
Реальный OpenRouter затем проверен отдельно:
[живой прогон](live-assistant.md), модель выбрана в D-127.
Публичный TLS и сторонний MCP-клиент остаются отдельной проверкой после деплоя.

## Проверки интегратора Users/Assistant — 12.11.2026

Рантайм и generation worker проверялись как одна реализация;
второй OAuth/LLM стек не добавлялся.

Выполнены проверки новых запросов генерации и worker с реальным PostgreSQL:

```sh
docker compose -f compose.test.yaml run --rm --no-deps tests \
  pytest -q apps/assistant/tests/test_generation.py
```

Результат: **8 passed, 4.66 s**. Проверены одна обработка при конкурентной
отправке, идемпотентный повтор, отказ для архива/отсутствующей конфигурации,
завершение через настоящий `Agent.run(TestModel)`, grounding предложения,
сохранение SDK-истории, освобождение слота при ошибке, поздний ответ в исходный
архивный чат и завершение исчерпанной SQL lease. История тестов сохраняется
только в случайных схемах отдельной тестовой БД; после проверки схемы удаляются.

Дополнительно выполнен `test_generation_mcp.py` в Docker с `--network none`:
**1 passed, 3.74 s**. Тест поднимает настоящий Gateway MCP SDK endpoint
на loopback TCP-порту и проходит путь `Agent(TestModel)` → `MCPToolset` → HTTP
MCP → проверенный пользователь → `prepare_booking`. Проверены передача
делегированного bearer, отсутствие инструментов изменения/отмены у модели,
возврат grounded proposal и отсутствие bearer в SDK-истории. Users introspection
и прикладной callback подготовки в этом тесте детерминированные: результат
доказывает совместимость SDK/транспорта, а не весь сценарий каталога/броней.
Во всех тестах `models.ALLOW_MODEL_REQUESTS=False`; платных обращений нет.

После передачи исправлены две обнаруженные границы:

- Рантайм принимает частичное предложение и абсолютную форму с каноническим
  `PUBLIC_BASE_URL`, сохраняя grounding по точному результату MCP. Отдельные
  тесты запрещают чужой origin, credentials и fragment.
- `generation_worker.delegate_token` переведён на `service_client`/
  `ServiceTransport`, то есть Core NATS при включённом RPC по D-124.

Повторный прогон `test_llm_runtime.py test_generation.py` после этих правок:
**32 passed, 6.02 s**. Настоящий MCP HTTP endpoint в тесте дополнительно
возвращает частичное предложение с абсолютной ссылкой разрешённого origin;
ответ проходит `Agent.run(FunctionModel)` и grounding. Платных LLM-вызовов нет.

После добавления передачи корреляции: `test_llm_runtime.py` —
**23 passed, 4.42 s**. Два параллельных запуска передают свои bearer,
`X-Request-ID` и `X-Trace-ID` без смешивания и без сохранения этих значений
в SDK-истории. В текущем SDK `MCPToolset.headers` несовместим с явным
`http_client`, поэтому заголовки задаются на собственном клиенте запуска.
