# Интеграция фронтенда с Gateway

Состояние на 12 ноября 2026 года. React в `apps/frontend` работает с
реальными сервисами через общий [GatewayClient](../../apps/frontend/src/shared/api/client.ts)
и `/api/` того же origin. Ошибка сервера не переключает интерфейс на демоданные.
Решения и альтернативы: [UI-005](decisions.md#ui-005-серверный-режим-и-сохранение-браузерного-архива).
Ниже описаны серверные контракты интерфейса и исторические локальные проверки.

## Подключено

| Область                     | Поведение интерфейса                                                                                                                                                                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Авторизация                 | Серверные вход, выход и восстановление cookie-сессии; общий клиент обновляет access-сессию. Браузерные демоучётки не используются.                                                                                                                           |
| Пользователи                | Список, создание и редактирование сотрудника, роль, доступ к офисам, отключение, смена и сброс пароля через Users/Gateway. Отзыв доступа и обработка броней имеют отдельный серверный статус.                                                                |
| Офисы                       | Серверный список и создание, отдельное сохранение имени, адреса и недельного расписания. Пустой успешный список отличается от ошибки загрузки.                                                                                                               |
| План                        | Загрузка офиса и автосохранение этажей через `PUT /api/offices/:id/plan`. Открытие плана само по себе не создаёт запись.                                                                                                                                     |
| Брони                       | Загрузка записей офиса, создание, редактирование формой, перенос и изменение границ на шкале, отмена; административная форма поддерживает выбор владельца.                                                                                                   |
| SSE                         | Один поток `/api/events` с авторизацией через cookie; `ready`, `resync` и события офисов, броней и чата запускают повторное HTTP-чтение соответствующих данных. Возврат фокуса также обновляет снимки.                                                       |
| История чата                | Текущий диалог, список архивов, просмотр архива и новый диалог через серверные `/api/chats/*`. Сворачивание сохраняет текущий диалог и черновик в интерфейсе. Возможности помощника читаются отдельно.                                                       |
| Генерация                   | Отправка сообщения с ключом идемпотентности, получение статуса, восстановление `request`/`processing` и предложения из HTTP-снимка; SSE запускает обновление.                                                                                                |
| Предложение и подтверждение | Новый ожидаемый ответ встроенного помощника сразу открывает проверенную форму на карте. Внешняя ссылка `/booking?officeId=…&floorId=…&resourceId=…` сохраняется для MCP и проходит через вход. Дата/время/участники необязательны, прошедшая дата очищается. |

Карточки и история используют `reviewReasons`, `resourceSnapshot`, `cancellationReason`
и `warnings`. Причины показаны понятными фразами; неизвестные коды не выводятся.
Исторические и удалённые ресурсы сохраняют имя и этаж из снимка брони. Свои отменённые
записи доступны в раскрытии «Мои брони», административные — в истории расписания.
Отменённые записи не увеличивают active-бейдж и открываются без редактирования.
При подтверждённом усечении начавшегося интервала показывается причина досрочного
завершения и фактически использованное время. Предупреждение о вместимости
не запрещает сохранение — [UI-008](decisions.md#ui-008-история-брони-использует-сохранённые-сведения-о-ресурсе).

Админка получает `GET /api/access-operations` и отдельные receipts по ID из
`X-Access-Operation-ID`. Публикация события и успешный PATCH не означают завершение
обработки броней: до серверного receipt статус остаётся `pending`. Счётчики отмены
и завершения берутся из ответа `completed`. Пока страница видима и есть pending,
статус проверяется GET-запросами; команды пользователя не повторяются.

План, настройки офиса и изменения/отмена брони передают исходную `revision`.
Ответ `409` не вызывает автоматический повтор с новой версией: пользователь
видит ошибку и может сверить актуальное состояние. Конструктор сохраняет
черновик восстановления и не заменяет новые локальные правки поздним ответом.
Создание брони и импорт офиса используют ключи идемпотентности.

По новому пользовательскому уточнению после успешного создания/изменения форма
закрывается, нужная группа Ганта раскрывается, а полоса прокручивается вертикально
в центр с ограничением по краям. Перенос/resize используют тот же результат.
Одноразовый focusBooking не повторяется от фонового чтения. Редактируемая полоса сохраняет
тень, соответствующую hover, до следующего реального наведения на любую полосу, затем работает
обычный hover. День остаётся целиком без новой горизонтальной прокрутки —
[UI-020](decisions.md#ui-020-после-сохранения-гант-показывает-и-выделяет-нужную-бронь).
После уточнения пользователя собственные редактируемые брони выделяются мягкой
размытой тенью и видимыми допустимыми resize-ручками; прежняя усиленная обводка
убрана. У начавшейся брони сотрудника доступна только правая ручка окончания.
Hover и saved-pin используют только тень и только для editable-полос. Read-only,
сводные и наследованные полосы не получают shadow-подсветку или grab-курсор,
сохраняя просмотр. Чужие полосы не получают постоянное own-оформление, общие
цвета занятости сохраняются. Клавиатурный focus-visible остаётся для доступности
и не является hover-подсветкой. Уточнённое оформление проверено по исходникам
и CSS, полная Docker-сборка прошла; предел браузерного подтверждения описан ниже.

При сбое фонового чтения офисов последний подтверждённый список остаётся
видимым, форма с несохранёнными правками не размонтируется. При ошибке чтения
занятости доступность считается неизвестной, создание и перенос отключаются.
Ответы предыдущей сессии не применяются к новому пользователю.

## Браузерный архив

Прежние ключи офисов, пользователей и броней не очищаются и не служат рабочей
серверной базой. Администратор может явно перенести сохранённый план из блока
«Сохранённые планы этого браузера» на странице офисов. Импорт через
`POST /api/offices/import` сохраняет ID офиса, этажей и предметов; повтор одной
попытки использует прежний ключ идемпотентности. Исходный архив остаётся на месте.

Пользователи и брони архива автоматически не импортируются. Старые владельцы
не сопоставляются новым серверным учёткам по имени или логину. Для переноса этих
данных потребуется отдельное явное сопоставление. В браузере также остаются
предпочтение выбранного офиса, черновики восстановления и квитанции попыток импорта.

## Граница помощника

Подключены `POST /api/chats/:id/messages` и `GET /api/generations/:id`.
Отправка доступна только при `generationAvailable=true`. Снимок `processing`
учитывает незавершённый запрос в другом диалоге; поздний ответ остаётся
в исходном архивном диалоге. `proposal` восстанавливается из сообщения после reload.

Новый ожидаемый ответ текущего диалога со структурированным `proposal` сразу
открывает заполненную форму на карте. Проверяются поля, доступный офис и реальный
ресурс; для другого разрешённого офиса выбирается его контекст. Переход по URL,
перезагрузка и дополнительный клик для первого открытия не нужны. Поле `url`
модели не используется для навигации; сырой адрес в тексте встроенного помощника
скрывается. Кнопка остаётся для повторного открытия, в том числе из архива.

Однократный guard связывает ожидавшийся pending/running request с текущей session.
Исходный completed из истории, ответ другого/архивного диалога и повторный SSE
не открывают форму автоматически. Ручная смена офиса очищает старое предзаполнение,
поэтому A→B→A его не повторяет. Неверное предложение не меняет выбранный офис.
Открытие формы не отправляет команду создания брони: требуется явное подтверждение.
Реализация и пересмотр прежнего перехода по ссылке —
[UI-009](decisions.md#ui-009-новый-ответ-помощника-сразу-открывает-форму-в-интерфейсе).

Для стороннего MCP-клиента по-прежнему строится безопасный URL нашей формы
из структурированных параметров. Он сохраняет query через вход; отсутствие
полей и прошедшая московская дата обрабатываются без молчаливой подстановки.
Переход по внешней ссылке также не создаёт бронь и не обходит проверку прав.

После первого открытия панель помощника остаётся смонтированной при сворачивании.
Крестик, Escape и открытие формы меняют видимость, сохраняя сообщения, запрос
и неотправленный черновик. Launcher предлагает «Продолжить диалог» либо показывает
«Подбираем место…». Это не архивирование: диалог завершается успешным созданием
новой брони или явной командой «Новый диалог». Серверная переписка восстанавливается
после reload, хранение неотправленного draft через reload не обещается —
[UI-010](decisions.md#ui-010-свёрнутый-помощник-сохраняет-незавершённое-обращение).

Карточки и диалоги используют устойчивую квадратную область закрытия 34×34 px,
padding 0 и SVG 18×18 px. Крестик закреплён вне прокручиваемого содержимого;
заголовки оставляют ему место —
[UI-011](decisions.md#ui-011-крестик-имеет-устойчивую-область-нажатия-вне-прокрутки).

В локальном прогоне 12.11.2026 OpenRouter был включён с выбранной пользователем
моделью `~deepseek/deepseek-flash-latest`; `generationAvailable=true`.
Живой прогон подтвердил поиск → заполненную форму → явное подтверждение
→ ровно одну бронь → архив чата: [отчёт и доказательства](live-assistant.md).
Контрольная бронь отменена. В этом фронтовом прогоне дополнительно проверено чтение
реального ответа и единственного предложения из архива; новый платный запрос
для этого не отправлялся.

Архивирующее событие `chat.changed` с `sessionId:null` и `archivedSessionId`
перечитывает текущий диалог и архив, сохраняя отсутствие активного чата. Оно
не создаёт новый диалог автоматически. Ручное бронирование от генерации не зависит.
Публичный HTTPS и сторонний MCP-клиент этим локальным прогоном не подтверждаются.

## Запуск

Из корня монорепозитория:

```bash
make up
```

Вход через Nginx: [бронирование](http://localhost:5178/booking) и
[Gateway API](http://localhost:5178/api/docs). Первого серверного администратора
создаёт явный bootstrap из [инструкции запуска](backend-foundation.md).
Установка зависимостей и запуск приложений выполняются только в Docker.

## Проверки

Ниже сохранены результаты локальных проверок от 12.11.2026. Они не являются
отчётом о текущем состоянии развёрнутого приложения. Дата 13 ноября в сценариях
обозначает дату тестовой брони.

```bash
docker run --rm --network none \
  --mount "type=bind,src=$PWD/apps/frontend/src,dst=/workspace/apps/frontend/src,readonly" \
  workplace-booking-frontend-dev npm test
docker compose -f compose.dev.yaml exec -T frontend npm run build
```

На подтверждённом прогоне до уточнения оформления UI-020 в Docker прошли
236 unit-тестов в 15 файлах и полная TypeScript/Vite-сборка. После последней правки
editable-only/shadow-only полная TypeScript/Vite-сборка в Docker прошла повторно;
unit-тесты в этот раз не запускались. В число ранее пройденных тестов входят guard однократного
открытия нового proposal и правила представления текста; автоматическое открытие нового completion
проверено тестами и не выдаётся за новый живой браузерный вызов LLM.
В браузере подтверждены серверный вход, явный импорт плана, создание,
перенос, редактирование и отмена брони, отказ устаревшей записи с `409`,
сохранение настроек и `PUT` плана. После перехода сервисов на NATS повторены
создание/отмена, выход, вход с восстановлением формы из URL, пустая дата старой
ссылки, отказ для недоступного офиса и ручное переключение A→B→A без повторного
предзаполнения. В этих прежних прогонах проверочные брони отменены,
временные настройки/план возвращены.
Дополнительно в браузере проверены загрузка админки с GET access-operations,
история собственных отмен и её карточка без возможности редактирования.
Сценарии pending/completed, поздних ответов, ошибок receipt и nullable-события
архивирования покрыты изолированными тестами. Это проверка локального dev-стенда;
живой вызов LLM подтверждён отдельным отчётом выше.

Браузерная проверка окон и помощника подтвердила область X 34×34 px, SVG 18×18 px,
padding 0 и попадание в центр кнопки. При scrollTop 370 крестик карточки сохранил
координаты; в «Моих бронях» размер тот же. В профиле и создании офиса кнопка
визуально центрирована и не перекрывает текст. Сворачивание сохранило черновик,
launcher показал «Продолжить диалог». Ручное повторное открытие существующего
proposal заполнило «Кабинет · место 4», 13 ноября, 11:00–18:00, без смены URL
и с сохранением zoom 38%. Этот прогон фронтенда не отправлял новых LLM/booking
команд. Пользовательские записи не изменялись и не отменялись ради этой проверки.

Отдельный последующий прогон UI-020 выполнен на контрольной брони 13 ноября,
09:00–10:00, «Место 1». Перед сохранением группа была свёрнута: успешное создание
закрыло форму, раскрыло группу и отцентрировало полосу (отклонение 0,5 px,
scrollTop 110). Закреплённое выделение сохранилось после смены фильтра и исчезло
при реальном движении указателя на полосу. Сохранение окончания 09:55 повторило
фокус; перенос в «Место 2» тоже закрыл карточку и отцентрировал полосу
(отклонение 0,5 px, scrollTop 145). Подсветка после переноса сохранилась при
неподвижном указателе. В той редакции у собственных полос обе разрешённые ручки
были видимы без hover, присутствовали постоянная обводка и тень; оформление
позднее пересмотрено в UI-020. Контрольная бронь отменена; пользовательская
бронь и прочие записи не изменялись. Новых вызовов LLM не было.

Последняя проверка оформления включает сборку, чтение исходников/CSS
и скриншот текущего состояния без наведения.
is-editable требует собственника либо canManageAll, отсутствия inherited,
открытого рабочего дня и editMode не none; is-movable доступен только для all,
закреплённая pin-подсветка — только editable. Проверены мягкая постоянная тень
own+editable, более размытая hover/pin-тень editable, отсутствие дополнительной
обводки, filter, светлого кольца и отдельной фиолетовой own-границы. Read-only
и сводные полосы не получают эту подсветку; клавиатурный focus-visible сохранён.
На скриншоте timeline-soft-shadow.jpg (артефакт рабочего чата вне репозитория)
видна активная собственная полоса с мягкой тенью и двумя ручками, а оранжевая
сводная полоса — без внешней обводки и тени. Это визуальная проверка состояния
без наведения: computed-стили живого hover не проверялись. Записи для этой проверки
не создавались и не изменялись; действия пользователя по разнице вкладок
не устанавливались.

Перед подготовкой production-сборки 12.11.2026
повторены полные Docker-проверки уже после последнего уточнения теней:
236 тестов в 15 файлах и TypeScript/Vite build прошли. Входной bundle —
`assets/index-DFxg42aj.js`. Аудит исходников не выявил фронтовых блокеров:
