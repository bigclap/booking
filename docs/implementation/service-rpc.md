# Core NATS для Users, Booking и Assistant

Обычные внутренние запросы используют официальный `nats-py` и Core NATS
request/reply по D-124. Готовые Pydantic/FastAPI-обработчики сервисов вызываются
внутри процесса через `httpx.ASGITransport`: сетевого HTTP-перехода к сервису нет,
валидация и транзакции остаются общими для обоих адаптеров.

## Контракт v1

Subjects: `rpc.workplace.users.v1`, `rpc.workplace.booking.v1`,
`rpc.workplace.assistant.v1`. Queue groups: `<service>-rpc-v1`. Ответ идёт
в созданный `nats-py` inbox. Эти subjects находятся вне JetStream `workplace.>`;
обычные запросы и ответы не сохраняются как бизнес-события.

Запрос: `{version:1, method, path, headers, query, payload, body?}`. Path допускает
`/internal/...`, два health-маршрута и OAuth endpoints Users. Заголовки передаются по закрытому
списку: служебный ключ, удостоверенный контекст, ID исполнителя/сессии,
корреляция, ключ идемпотентности, версия и делегированное MCP-полномочие.
Ответ: `{version:1, status, headers, payload, body?, cookies}`. Для стандартных OAuth
форм и HTML/redirect сохраняются исходные байты, тип содержимого и отдельные
Set-Cookie; JSON внутренних DTO остаётся типизированным payload. Публичные DTO и права остаются
обязанностью Gateway. Формат ошибок обработчиков сохраняется.

`ServiceTransport` маршрутизирует только настроенные origins Users/Booking/Assistant.
Остальные адреса используют обычный HTTP-транспорт; это сохраняет MCP-вход
Gateway и внешние провайдеры. Все обработчики дополнительно проверяют служебный
ключ; NATS и сервисы не публикуют порты наружу.

## Запуск и сбои

В Compose включён `INTERNAL_RPC_ENABLED=true`; без него приложение можно
тестировать в процессе через существующий HTTP/ASGI-адаптер. Подписки создаются
после инициализации БД и закрываются перед её освобождением. Независимые RPC
обрабатываются конкурентно с ограничением одновременно исполняемых обработчиков.

Нет автоматического повтора RPC: потеря ответа изменяющего запроса не доказывает,
что транзакция не была зафиксирована. Повтор создания брони использует прежний
`Idempotency-Key`. Нет responder или истёкший тайм-аут становятся ошибкой
недоступности upstream. Надёжные действия используют отдельные outbox/JetStream
обработчики с подтверждением после фиксации результата.

NATS допускает сообщения до 16 MiB для документов планов с изображением;
это технический предел транспорта, не новая бизнес-квота. Более крупные подложки
нуждаются в отдельном хранении файлов. `request_id`/`trace_id` передаются
сквозь RPC и доступны outbox через `workplace_platform.correlation.event_metadata()`.
Тела запросов и токены в общие журналы не выводятся.

## Выбор реализации

- **Выбрано:** официальный `nats-py` и общий адаптер существующих типизированных
  обработчиков. Это даёт один набор проверок и транзакций без переписывания
  доменов под транспорт.
- **Альтернатива:** FastStream. Полезен для большого набора самостоятельных
  broker handlers; здесь добавил бы второй lifecycle/DI-слой поверх уже работающего
  FastAPI. При развитии проекта адаптер можно заменить, сохранив envelope.
- **Альтернатива:** внутренний сетевой HTTP. Отклонён решением D-124.

Проверки: `packages/platform/tests/test_rpc_integration.py` использует настоящий
изолированный NATS: конкурентные запросы, ключ доверенного сервиса, корреляция,
query/JSON/204, тайм-аут без повтора и отсутствие RPC в JetStream.

Дополнительно 12.11.2026 выполнен
`test_transport_accepts_plan_above_default_nats_limit_and_rejects_oversize`:
**1 passed, 1.50 s**. Через реальный NATS прошёл круг JSON с подложкой 1100 KiB;
запрос с 17 MiB получил 413 до вызова обработчика. Маленький запрос, для которого
обработчик сформировал ответ 17 MiB, получил короткий `413 rpc_payload_too_large`
вместо тайм-аута. Ruff check/format check этого теста прошли.
Ошибка размера ответа сама по себе не означает откат уже завершённой транзакции;
повтор изменяющей операции использует её прежний ключ идемпотентности.
