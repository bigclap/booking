# Реализация Booking

Проверено 12.11.2026 в отдельном Docker-стенде `compose.test.yaml` с настоящими
PostgreSQL и NATS. Эта запись описывает серверный домен; она не подтверждает
готовность публичного развёртывания, фронтенда или платного вызова LLM.

## Данные и правила

Booking хранит здания, недельные часы, этажи и полные документы конструктора.
Строковые ID и дополнительные поля плана сохраняются. План и его проекция
бронируемых ресурсов меняются атомарно; настройки часов сохраняются отдельно.
Удалённые этажи и ресурсы остаются историческими записями. Неверные геометрические
значения, циклы и конфликты идентификаторов отклоняются до сохранения.

Брони следуют московской дате, сетке и горизонту из конфигурации. Проверяются
рабочие часы, серверное время, участники переговорной и режим бронирования мест.
Соседние интервалы совместимы, разные места при включённом общем режиме
совместимы, комната несовместима с местами внутри неё.

Транзакционная блокировка PostgreSQL по зданию сериализует операции записи
броней и изменение условий. Она работает между процессами сервиса, а не только
в памяти Python. Подтверждение дополнительно сериализовано по паре
`actor_id + Idempotency-Key`; результат и отпечаток параметров сохраняются в БД.
Повтор возвращает ту же бронь, изменённый запрос с тем же ключом — отдельную ошибку.
Широкая блокировка здания выбрана ради простой проверяемой корректности тестового;
оптимизация пропускной способности не заменяет эту защиту.

Изменения условий сохраняют действующие брони и добавляют `needs_review` с
`review_reasons`. Исходный интервал продолжает блокировать использование.
Снимок ресурса содержит название, этаж, оснащение, вместимость и исходные
дочерние ресурсы; удаление или переподчинение комнаты не освобождает незаметно
места уже согласованной брони. Простого ознакомления для снятия пометки нет:
нужно допустимое изменение или отмена. Автоматической проверки изменившегося
оснащения по-прежнему нет.

`booking_mutations` хранит снимок каждой версии: создание, изменение, отмену,
пересмотр и утрату доступа. Для старых данных миграция создаёт честную запись
`migrated_baseline`, не выдумывая отсутствующую прежнюю историю. Досрочное
окончание хранится точно, без округления; `scheduled_ends_at` сохраняет
согласованное окончание. Повтор отмены возвращает её прежний результат.

Вместимость берётся из явно заданного `equipment` с количеством сидячих мест
вида (например, диван на три места), либо из `seats` старого документа.
Близость предметов на плане не назначает оснащение автоматически. Превышение
вместимости возвращается как `warnings: [{code: "capacity_exceeded", ...}]`
и не запрещает создание.

## Внутренний контракт

Прикладные обработчики `/internal` доступны только за доверенным ключом.
Обычный межсервисный транспорт подключается общим адаптером Core NATS;
внутрипроцессный вызов тех же обработчиков не создаёт вторую копию правил.
Проверки личности, роли, доступа к зданию и владельца принадлежат Gateway.
Booking не содержит локального списка пользователей или выданных им прав.

Помимо прежних операций офисов и броней добавлены:

- `GET /internal/offices/{office_id}/bookings/{booking_id}/history` — версии
  брони с операцией, снимком и временем записи.
- `POST /internal/offices/{office_id}/availability` — тело
  `{floor_id,date,start,end,cursor?,resource_id?,exclude_booking_id?}`.
  Для каждого ресурса возвращаются доступность всего интервала,
  конфликтующие ID, ошибка политики времени, отдельный `cursor_status`
  (`free`, `partial`, `occupied`), число конкретных бронируемых мест
  и число занятых мест. Исключение собственной брони для редактирования
  разрешает Gateway.
- Ответы броней дополнены `review_reasons`, `resource_snapshot`,
  `cancellation_reason`, `warnings`. Каталог ресурсов дополнен
  `capacity` и `equipment`. Прежние обязательные поля сохранены.

### Административное исправление данных

Внутренние JSON-схемы `CreateBookingInput`, `UpdateBookingInput` и
`CancelBookingInput` содержат строго булевый `administrative`, по умолчанию
`false`. Это режим уже разрешённой команды, а не хранимая роль пользователя.
Gateway сам выставляет `true` только для административного HTTP-сценария;
публичное тело запроса и MCP сотрудника не назначают этот режим.

По D-042 административная команда может создавать и исправлять прошлые
записи, менять начавшуюся бронь и работать за обычным горизонтом сотрудника.
Ограничения серверного «сейчас», горизонта и фиксации начала/ресурса текущей
брони в этом режиме не применяются. Сетка, московская дата, действующие
недельные рабочие часы, доступность ресурса, число участников и физические
конфликты проверяются в полной мере. Проверки Gateway по правам остаются
обязательными; административный режим не добавляет их копию в Booking.

Административная отмена уже прошедшей записи сохраняет её интервал и
историю, а текущую завершает сейчас. Причина — `admin_cancelled`;
исходный владелец не подменяется администратором. В снимке истории и
outbox записывается `administrative`. Режим привязан к идемпотентному
подтверждению: переключение режима с тем же ключом — несовместимый повтор.
Обычный `false` сохраняет отпечатки подтверждений прежней версии сервиса.

Изменения пишутся в outbox одной транзакцией с данными и историей. Событие
брони содержит владельца, здание, текущие и затронутые этажи/ресурсы,
интервал, тип изменения, версию и доступные `request_id`/`trace_id`.
Повтор подтверждения не создаёт второе событие создания.

## Надёжный отзыв доступа

JetStream worker `workplace_booking.user_events` обрабатывает отключение
пользователя и отзыв отдельных зданий. Receipt inbox фиксируется вместе с
изменениями; ACK отправляется после commit. При ошибке транзакция откатывается
и сообщение получает NAK для повтора.

Команда использует исходный `occurred_at`: доставка после простоя не сдвигает
время отзыва и не захватывает брони, созданные после этого момента.
Будущие на тот момент отменяются, текущие завершаются на исходной границе,
история и другие здания сохраняются. Никакой пользовательский реестр
для проверки новых запросов в Booking не добавляется.

При наличии `operation_id` в той же транзакции создаётся событие
`workplace.booking.access_revocation_completed` с `operation_id`, `user_id`,
`cancelled_count`, `terminated_count`, `effective_at` и корреляцией.
Users использует результат для промежуточного/итогового состояния операции.
Повтор доставки исходного event ID не меняет бронь и не дублирует результат.

## Проверки

Исторический прогон от 12.11.2026 выполнен в **изолированном** стенде:

```bash
docker compose -f compose.test.yaml run --rm --no-deps tests pytest apps/booking/tests -q
```

Результат: **72 passed**. Набор включает 100 одновременных TCP HTTP-запросов
на один ресурс и 100 запросов на комнату/её место; в каждом случае один успех,
остальные — конфликт, в БД одна бронь, одна запись подтверждения и одно событие.
Проверены соседние интервалы, разные места, повтор ключа, конфликтный перенос,
начавшаяся бронь, пометки, снимки удалённых ресурсов, история, вместимость,
отдельные состояния курсора и интервала, точный отзыв и повторная доставка JS.
Отдельно проверены прошлые/начавшиеся административные исправления и даты
за горизонтом, сохранение запрета конфликтов/шага/часов и обычные ограничения
сотрудника при `administrative=false`.
Ruff check и format для `apps/booking` прошли внутри Docker 12.11.2026.

Защитный эксперимент выполнен в отдельном процессе контейнера: функция
`bookings.check_conflicts` временно заменена на no-op только в памяти,
затем запущен тот же concurrent test. Он завершился **FAIL** на проверке
`assert 100 == 1`: ошибочно сохранились все сто запросов.
Исходники и рабочие контейнеры эксперимент не менял. Запуск обычного теста
в свежем процессе после эксперимента подтверждает восстановленную защиту.
Воспроизводимая полная процедура: `sh scripts/prove-booking-guard.sh`.

Публичный Gateway, авторизованный SSE, живые MCP-клиенты, интеграция
конструктора и пользовательские сценарии интерфейса проверяются отдельно.
Автоматического импорта браузерных данных и перезаписи dev/prod-данных нет.
