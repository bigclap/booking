# Users, Booking и Assistant: состояние реализации

Исторический отчёт о коде и проверках от 12.11.2026; требования остаются в
`docs/spec/`, бизнес-решения — в `docs/decisions.md`. Существующий код дополнен
с сохранением параллельной реализации Gateway и фронта.

## Реализовано

| Сервис    | Поведение                                                                                                                                                                                                                                                                                                     |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Users     | Логин/пароль, администрирование сотрудников и зданий доступа, короткий JWT, refresh без календарного предела, отзыв сессий, официальный OAuth/PKCE MCP provider, делегирование, долговечное состояние отзыва доступа и результата Booking                                                                     |
| Booking   | Планы и каталог, политика времени, атомарные создание/изменение/отмена, идемпотентность, конфликты комнаты и мест, пометка пересмотра с причинами, исторические снимки/версии, доступность интервала и занятость курсора, предупреждение вместимости, административное исправление, выполнение отзыва доступа |
| Assistant | Общий диалог пользователя, архив, одна генерация на пользователя, восстановление состояния, outbox и SQL lease worker, Pydantic AI/OpenRouter через общий MCP, изолированные полномочия, ограничение инструментов, контекст целыми группами, предложения только из фактического prepare_booking               |

Обычные внутренние обращения используют Core NATS. Надёжные события и результаты
идут через transactional outbox и JetStream с inbox-подтверждением после commit.
MCP остаётся HTTP Streamable HTTP. Роли и объектные права проверяет Gateway;
Booking не хранит проекцию пользовательских полномочий.

Делегированные MCP-токены не сохраняются в запросе генерации и не попадают
в промпт/SDK-историю. Worker получает полномочия исходной сессии заново;
Users отказывает после её отзыва. `origin_request_id` и `trace_id` переживают
очередь генерации и передаются в делегирование и HTTP MCP отдельно от ID запуска.

Предложение может частично заполнить форму. Допускается относительная ссылка
`/booking?...` либо абсолютная ссылка с каноническим `PUBLIC_BASE_URL`.
Чужие адреса, credentials и фрагменты отклоняются. Предложение не создаёт бронь.

## Проверки

Полный серверный набор от 12.11.2026 в отдельном временном проекте Compose:

```sh
docker compose -p workplace-services-proof -f compose.test.yaml up -d --wait postgres nats
docker compose -p workplace-services-proof -f compose.test.yaml run --rm --no-deps tests pytest -q --tb=short
```

**286 passed, 39.53 s.** Настоящие PostgreSQL и NATS/JetStream; LLM в автотестах
детерминированная, платных вызовов эти проверки не выполняют. Ruff check и
format check прошли для `packages apps scripts` — 122 Python-файла.

Покрыты реальные конкурентные запросы бронирования, room/place-конфликты,
повтор подтверждения, история, административные исправления, OAuth/PKCE,
конкурентный обмен кода и отзыв токенов, восстановление генерации, изоляция
параллельных MCP-сессий и сквозная цепь трёх сервисов:

`создание брони → архив чата → отключение сотрудника → отмена Booking → результат Users`.

Проверка защиты с временной подменой `check_conflicts` только внутри тестового
процесса обнаружила 100 ошибочных успехов вместо одного. После восстановления
тот же конкурентный тест прошёл. В production-коде выключателя защиты нет.

Проверен транспорт: сообщения планов больше 1 MiB, явная ошибка превышения
16 MiB, RPC вне JetStream, отсутствие автоматического повтора при потере ответа,
OAuth HTML/forms/redirects/Basic/preflight и отсутствие cookie между пользователями.

## Dev и конфигурация

Во время проверки 12.11.2026 миграции применены через Docker, запущены локальные
API/worker-процессы и пройден `make smoke`. Через NATS получены 200 для каталога Booking, его readiness и OAuth
discovery Users. Единый вход — `http://localhost:5178`; рабочие данные и
браузерные архивы не очищались.

OpenRouter подключён через игнорируемый `.env`; пользователь выбрал
`~deepseek/deepseek-flash-latest` по D-127. `generation_available=true`.
Проверен реальный браузерный путь: поиск через MCP → заполненная форма →
подтверждение → одна бронь → архив чата. Контрольная бронь отменена,
история сохранена. [Результат живого прогона](live-assistant.md).
Настройки `PUBLIC_BASE_URL`, постоянный `MCP_ENCRYPTION_KEY`, политика времени
и другие переменные перечислены в `.env.example`/`.env.prod.example`.
Генерация запускается отдельным `assistant-generations`, публикация —
`assistant-outbox`; ручное бронирование не зависит от доступности LLM.

Живой вызов OpenRouter подтверждён отдельно от указанного выше общего набора
автотестов; исправление обработки MCP-ошибок покрыто 26 целевыми тестами.
Публичный HTTPS и подключение стороннего OAuth/MCP-клиента требуют отдельной
проверки. Локальные тесты и smoke не подтверждают эти внешние сценарии.

## Контракты и решения реализации

- [Users](users-service.md): миграции, операции отзыва и worker результатов.
- [Booking](booking-service.md): бизнес-инварианты, история и внутренний administrative-флаг.
- [Assistant](assistant-runtime-handoff.md): DTO, runtime, границы LLM/MCP-проверок.
- [Core NATS](service-rpc.md): envelope, subjects, lifecycle, ошибки и альтернативы адаптера.
- [Передача фронту/Gateway](backend-handoff.md): HTTP, SSE, версии и идемпотентность.

Используется одна OAuth-реализация официального MCP SDK: параллельный вариант
на других примитивах удалён до интеграции. Выбрана долговечная очередь генераций
с SQL lease вместо фоновой задачи только в памяти API. Служебные HTTP-клиенты
не сохраняют cookie, а каждый LLM/MCP-запуск получает отдельный клиент.
Альтернативы и мотивы NATS-адаптера описаны в отдельной заметке выше.
