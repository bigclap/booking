# Workplace Booking

Бронирование рабочих мест и переговорных на интерактивных планах этажей.
React-интерфейс включает план, расписание, формы, админку и помощника через
OpenRouter. Помощник подбирает ресурс через MCP и готовит форму; бронь создаётся
после явного подтверждения пользователя.

Репозиторий: [bigclap/booking](https://github.com/bigclap/booking).
Требования и история решений основаны на [исходном задании](docs/source/assignment.md).

## Структура

| Каталог             | Назначение                                              |
| ------------------- | ------------------------------------------------------- |
| `apps/frontend`     | React: пользовательский интерфейс и конструктор офиса   |
| `apps/gateway`      | FastAPI: HTTP API, MCP, SSE, авторизация и права        |
| `apps/users`        | FastAPI: пользователи, пароли, веб- и OAuth-сессии      |
| `apps/booking`      | FastAPI: офисы, ресурсы, расписание, брони и конфликты  |
| `apps/assistant`    | FastAPI и Pydantic AI: диалоги, OpenRouter и MCP        |
| `packages/platform` | Общие настройки, транспорт NATS, JWT и outbox           |
| `docs`              | Пять ТЗ, предметная модель, контракты и журналы решений |

Сервисы владеют отдельными БД PostgreSQL. Gateway вызывает их через Core NATS;
надёжные фоновые действия используют JetStream и transactional outbox.
Встроенный помощник и внешний агент обращаются к одному MCP Gateway с правами
сотрудника. Снаружи приложения доступны через один Nginx.

## Разработка

Нужны Docker Engine, Docker Compose и Make. Зависимости, приложения, миграции,
проверки и форматирование запускаются в Docker; Python и Node на хосте не нужны.
При необходимости создайте `.env` по [.env.example](.env.example), сохранив
существующее окружение.

```sh
make up
BOOTSTRAP_ADMIN_PASSWORD='задайте-свой-пароль-от-8-символов' make bootstrap
```

- Приложение: [localhost:5178/booking](http://localhost:5178/booking).
- API / Swagger: [localhost:5178/api/docs](http://localhost:5178/api/docs).

Первый администратор создаётся явно; повторный bootstrap не сбрасывает пароль.
Доступны переменные `BOOTSTRAP_ADMIN_LOGIN`, `BOOTSTRAP_ADMIN_FIRST_NAME`
и `BOOTSTRAP_ADMIN_LAST_NAME`. Новые БД пусты: создайте офис и сотрудников
через админку, настройте расписание, этажи и бронируемые ресурсы в конструкторе.
Автоматического наполнения офисами и бронями нет.

```sh
make ps
make logs
make down
```

`make down` сохраняет рабочие volumes. Python-зависимости фиксируются в `uv.lock`:
после изменения зависимостей выполните `make lock`, затем `make up`.
Подробности: [разработка](docs/implementation/backend-foundation.md#разработка)
и [интеграция React](docs/implementation/frontend-integration.md).

## LLM и MCP

Для генерации задайте в окружении Assistant:

```dotenv
OPENROUTER_API_KEY=ваш_ключ
OPENROUTER_MODEL=vendor/model-id
```

Укажите доступный вашему аккаунту ID модели OpenRouter вместо примера.
Ключ остаётся на сервере. Assistant использует Pydantic AI; генерации выполняет
отдельный worker. Без настроенного провайдера чат сообщает о недоступности,
а ручной путь бронирования сохраняется.

MCP доступен по `/mcp`, авторизация — OAuth Authorization Code с PKCE.
`PUBLIC_BASE_URL` задаёт канонический адрес приложения и ссылок на форму.
В production нужен постоянный `MCP_ENCRYPTION_KEY`; веб-JWT и MCP-токены имеют
разные жизненные циклы. Административных инструментов в MCP нет.
Контракты: [Gateway](docs/implementation/gateway-contract.md),
[Assistant](docs/implementation/assistant-runtime-handoff.md),
[транспорт](docs/implementation/service-rpc.md).

## Production

Создайте `.env.prod` по [.env.prod.example](.env.prod.example), заполните пароли БД,
служебные и JWT/MCP-ключи, настройки OpenRouter, `PUBLIC_BASE_URL`,
`ALLOWED_ORIGINS` и данные первоначального администратора.

```sh
make prod-config
make prod-up
make prod-bootstrap
make prod-down
```

[compose.prod.yaml](compose.prod.yaml) собирает отдельные образы сервисов
и статический frontend через Nginx. Production имеет собственные данные,
отдельные от [compose.dev.yaml](compose.dev.yaml). По умолчанию Nginx слушает
`127.0.0.1:8080`; для публичного доступа настройте HTTPS-прокси, DNS и сертификат.
Production cookies имеют `Secure`; `make prod-down` сохраняет данные.
[Подробная инструкция](docs/implementation/backend-foundation.md#production).

## Правила и ограничения

- Пользователей создаёт администратор. Вход по логину и паролю, без email;
  доступ назначается по офисам, внутри доступны все ресурсы.
- Московское время, одно рабочее окно на день недели. По умолчанию шаг —
  пять минут, горизонт — сегодня и ещё шесть дат; оба параметра настраиваются.
- Бронь комнаты конфликтует с её рабочими местами. Разные места бронируются
  параллельно при включённом совместном режиме. Один сотрудник может занять
  разные независимые ресурсы одновременно.
- Изменение условий сохраняет затронутые брони с пометкой пересмотра.
  Отзыв доступа отменяет будущие и завершает текущие, история остаётся.
- Подтверждение использует идемпотентность, редактирование — revision.
  Предложение помощника не удерживает ресурс; ссылка на форму не имеет TTL.
- Записи Booking сериализуются по зданию; высокий нагрузочный SLA не заявляется.
  Предел NATS RPC — 16 MiB вместе с envelope, превышение возвращает `413`.
- Полная мобильная приёмка, сохранность после отдельного сценария перезапуска
  и подключение стороннего ChatGPT-клиента остаются отдельными проверками.
- Отложены серии броней, исключения расписания по датам, внешние оповещения,
  автоматический пересмотр из-за оснащения и перенос/отмена через встроенный чат.

Причины и альтернативы — в [журнале решений](docs/decisions.md),
оставшиеся вопросы — в [docs/questions.md](docs/questions.md).

## Проверки и материалы сдачи

```sh
make test
make lint
make typecheck
make format-check
make smoke
make prod-smoke
sh scripts/prove-booking-guard.sh
```

Область строгой проверки Python и границы данных описаны в
[документе типизации](docs/implementation/python-typing.md).

Тесты используют отдельный временный PostgreSQL/NATS, без dev/prod БД.
Конкурентный тест отправляет 100 реальных HTTP-запросов к Booking и проверяет
результат в PostgreSQL. Эксперимент временно отключает защиту в одноразовом
процессе, подтверждает ожидаемое падение и повторяет тест с исходной защитой.

После очистки и переноса 13.11.2026 прошли 293 серверных и 236 фронтовых тестов,
TypeScript/Vite build, Ruff, Prettier и локальный production smoke.
Реальная LLM проверялась отдельно от этих детерминированных прогонов.
Команды, доказательства и оставшиеся проверки: [TESTING.md](TESTING.md).
